## Lesson: mla-config-rope-dim-derivation
Lesson ID: BL-20260527-mla-config-rope-dim-derivation
Scope: calibrate.py, any code reading DeepSeek MLA config fields
Problem Description: Deriving qk_rope_head_dim as `head_dim - qk_nope_head_dim` fails when head_dim is itself derived from `hidden_size // num_heads`. DeepSeek-V3.2 has hidden_size=7168, num_attention_heads=128 → head_dim=56, not 128+64=192. The derived value is negative, making full_mla_q_width=None and silently skipping all Q hooks; "Calibration hooks did not fire" is only raised much later.
Root Cause: DeepSeek MLA configs have qk_rope_head_dim as an explicit field but no head_dim field. Using hidden_size // num_heads as head_dim is valid for non-MLA models but wrong for MLA where per-head dims don't pack to exactly hidden_size / num_heads.
Solution: Always read config.qk_rope_head_dim directly first. Only fall back to head_dim - qk_nope_head_dim for configs that lack the field. Validate the fallback is positive and raise a clear error with all derived values if it is not.
Constraints: Applies to any code reading MLA per-head dimensions from HuggingFace configs (calibrate.py, model dimension inference code).
Validation Evidence: test_dsv32_real_config_shape_q_hook_fires uses hidden_size=32, num_heads=4 (hidden_size//num_heads=8 ≠ qk_nope+qk_rope=12); 188 passed.
Source Rounds: 13

## Lesson: reshape-before-slice-mla
Lesson ID: BL-20260527-reshape-before-slice-mla
Scope: calibrate.py, dsa_backend.py, any code consuming MLA projection outputs (kv_b_proj, q_b_proj)
Problem Description: Flat-slicing `tensor[..., :H*nope_dim]` before reshape on MLA projection outputs selects V or RoPE columns from later heads, producing silently wrong noPE activations. The output shape is correct; only the values are wrong. Triggered when tensor has shape `[T, H*(nope+suffix)]` and the intent is to extract only the noPE prefix per head.
Root Cause: MLA projections pack per-head blocks sequentially: `[K0_nope|V0|K1_nope|V1|...]` for kv_b_proj, `[Q0_nope|Q0_rope|Q1_nope|Q1_rope|...]` for q_b_proj. Flat-slicing the first `H*nope_dim` columns crosses head boundaries and includes suffix columns from head 0 as head 1's noPE values.
Solution: Reshape to `[-1, H, nope_dim + suffix_dim]` FIRST, then slice `[..., :nope_dim]`. Wrapped as `_extract_mla_nope_prefix(tensor, num_heads, nope_dim, suffix_dim)` in calibrate.py. The same fix was applied to dsa_backend.py in Round 3 (line ~1436: `kv_proj_out.reshape(T, H_local, nope_dim + v_head_dim)[..., :nope_dim]`).
Constraints: Only applies to MLA projections (kv_b_proj, q_b_proj). Standard attention projections (k_proj, q_proj) have no suffix dimension and use direct reshape.
Validation Evidence: `test_mla_k_extraction_ignores_v_columns` and `test_mla_q_extraction_ignores_rope_columns` use sentinel V/RoPE values of 100.0; both tests fail under flat-slice and pass under reshape-then-slice. 185 passed, 0 failed in Round 11.
Source Rounds: 3 (dsa_backend.py fix), 11 (calibrate.py fix + sentinel tests)

## Lesson: torch-topk-aliasing-corrupts-input
Lesson ID: BL-20260527-torch-topk-aliasing-corrupts-input
Scope: selection_kernel.py, any allocation-free CUDA-graph-safe pipeline using torch.topk with `out=` argument
Problem Description: When `torch.topk(input=A, k, ..., out=(values=B, indices=A))` aliases the output indices tensor with the input tensor, the read is corrupted. Symptom observed in Round 17: input int64 tensor `[3, 1]` produced sorted ascending output values `[0, 1]` instead of `[1, 3]`. The bug only manifests in step-3 of the topk pipeline (the "ascending sort via smallest-first topk" trick) when an earlier step's output indices buffer is reused as both the input AND the (throwaway) output of the next topk call.
Root Cause: PyTorch's topk implementation does not enforce input/output non-aliasing for the `indices` output channel. The dispatcher reads input and writes output indices interleaved in the same buffer.
Solution: Allocate a dedicated `scratch_throwaway_idx` tensor (int64 [max_bs, max_top_k]) for the discarded gather indices of the second `torch.topk` call. Never alias topk's input with its output indices buffer, even when the indices are not used afterward.
Constraints: Applies to any allocation-free pipeline that uses `torch.topk(..., out=...)` more than once on overlapping buffers. The values output may safely alias other unrelated tensors but the indices output must not alias the input.
Validation Evidence: `test_retrieve_topk_graph_safe_per_request_valid_masks_position` fails with `sorted([0, 1]) != [1, 3]` under aliasing; passes after introducing `scratch_throwaway_idx`. 197 passed, 0 failed in Round 17.
Source Rounds: 17

## Lesson: ds-metadata-via-forward-context
Lesson ID: BL-20260527-ds-metadata-via-forward-context
Scope: deepseek_v2.py::_select_topk_indices, dsa_backend.py::_ds_radix_publish_extend_snapshot (the radix-capture producer), any DS hook that needs to read the active attention backend, its `forward_metadata` (DSAMetadata), OR its `req_to_token` map — applies to other model files that gate on DS too.
Problem Description: Production publishes the active attention backend through `ForwardContext` (set by `cuda_graph_runner.py` and `model_runner.py`). Real `ForwardBatch` has NO `attn_backend` field and the CUDA-graph capture machinery constructs a fresh local `ForwardBatch` without DS-specific fields. Looking up `forward_batch.attn_backend.forward_metadata.<X>` silently returns None (or, with `MagicMock`, a fake auto-attribute) and the code falls through to a per-call lazy allocation (`torch.empty_like(...)`, `torch.empty(...)`). The bug is invisible in unit tests that mock `forward_batch.attn_backend` because the synthetic path mirrors the dead branch; only a `ForwardContext`-based probe exposes it.
Root Cause: Two source-of-truth paths for the attention backend exist in this codebase. `forward_batch.attn_backend` is documented on some unit-test fixtures but never set by `cuda_graph_runner.py` or `model_runner.py` in production. The DS path was historically written against the synthetic path.
Solution: Resolve DS metadata in `_select_topk_indices` in exactly this order: (1) `forward_batch.<field>` (set by `dsa_backend.init_forward_metadata` for dynamic non-graph forwards), (2) `has_forward_context() and get_attn_backend().forward_metadata.<field>` (real CUDA-graph capture/replay), (3) optionally a last-resort lazy allocation for CPU unit tests that synthesize forward_batch. Never look up `forward_batch.attn_backend.<X>` — it does not exist on production ForwardBatch and any unit test that mocks it is testing a dead path. When writing unit-test stubs for the backend, use `SimpleNamespace(use_mha=False, forward_metadata=...)` rather than `MagicMock()` so `getattr(backend, 'forward_metadata', None)` returns the intended None (or the explicit stub) instead of a polluting auto-attribute. Required regression: a CUDA test that publishes the field only through `ForwardContext`, spies `torch.empty_like` (call_count must stay 0), and asserts the returned tensor's `data_ptr` aliases the metadata buffer.
Constraints: Applies to any DS read-side hook that consumes per-batch attention-backend state during a forward pass. Does not apply to one-time bind-time data (those go through `server_args._*` attrs set by `finalize_double_sparsity_bind()`).
Validation Evidence: `test_select_topk_indices_uses_metadata_ds_topk_indices_out_via_forward_context` (spy on `torch.empty_like` + `data_ptr` aliasing); `test_select_topk_indices_zero_allocs_production_path` with the manual `forward_batch.ds_topk_indices_out` pre-set removed; 201 passed, 0 failed in Round 20. Symptom probe before fix: spy.call_count = 1 (one lazy `torch.empty_like` per call); after fix: 0.
Source Rounds: 18 (introduction of the synthetic path), 19 (partial fix for ds_graph_state only), 20 (full fix for both DS metadata fields); loop5 R3 (same defect class in the radix-capture producer `_ds_radix_publish_extend_snapshot`: production `ForwardBatch` has no `req_to_token_pool`, so the publish returned before writing `double_sparsity_radix_capture`; fixed with `_resolve_req_to_token_for_capture` — `forward_batch.req_to_token_pool.req_to_token` → `getattr(backend,"req_to_token",None)` → ForwardContext backend (TBO-unwrapped) — plus a production-shaped regression that omits `req_to_token_pool`. Also: do NOT wrap the required context lookup in a broad `except Exception`; that swallowed the `NameError`/missing-field and silently dropped the publish — the best-effort catch belongs only around the snapshot read, not the context resolution).

## Lesson: shell-json-into-python-source
Lesson ID: BL-20260527-shell-json-into-python-source
Scope: any dev script that captures a tool's JSON output (e.g. `curl /get_server_info`, `kubectl get -o json`, `aws ... --output json`) and then needs to emit a metadata sidecar via inline Python.
Problem Description: A bash script splices the captured JSON variable directly into a Python heredoc as source code:
```bash
SERVER_ARGS_JSON="$(curl -s ...)"
python3 - <<PYEOF
import json
print(json.dumps({"server_args": ${SERVER_ARGS_JSON}}))
PYEOF
```
Works fine in development against fixtures of strings + ints + dicts of those, then fails in production with `NameError: name 'true' is not defined` because real JSON contains `true` / `false` / `null` (valid JSON tokens, NOT valid Python identifiers). The crash happens AFTER the expensive task succeeds, so the operator gets the benchmark JSONL but no reproducibility metadata, and only notices when the AC-11 audit fails weeks later.
Root Cause: JSON and Python have overlapping but unequal value-literal grammars. JSON `true|false|null` and Python `True|False|None` are different tokens; JSON numbers and Python numbers agree by accident on the integer subset but disagree on `Infinity` / `NaN`. Direct shell interpolation into a Python heredoc treats the JSON text as source code, so any non-trivially-overlapping value crashes.
Solution: Pass the captured JSON to Python as DATA, never as source. Two safe patterns: (a) export the variable and read it via `os.environ.get(...)`, then `json.loads(...)` inside Python; (b) pipe the JSON on stdin and `json.load(sys.stdin)`. Prefer (a) when the heredoc also needs other shell vars. Always handle the empty/malformed cases (record `{}` plus an error string so the operator can diagnose offline). Use `<<'PYEOF'` (quoted heredoc delimiter) so bash leaves the Python source alone. Extract the writer into a standalone helper (e.g. `development/_bench_meta_writer.py`) so it's directly testable: a registered test can feed `{"a": true, "b": null}` and assert valid output.
Constraints: Applies to any dev/CI/operator script that bridges shell capture and Python emission of metadata. Same risk exists in reverse (Python → shell) for similar reasons; the fix there is `json.dumps` not f-string.
Validation Evidence: Round 23 sidecar writer crashed in `benchmark.sh:71-83` when `/get_server_info` returned `{"disable_radix_cache": true, "kv_events": null}`. Round 24 extracted `development/_bench_meta_writer.py` with `json.loads` from `SERVER_ARGS_JSON` env var; 10 registered tests in `test_bench_meta_writer.py` exercise realistic, empty, malformed, and non-object inputs. 229 passed, 0 failed.
Source Rounds: 23 (introduced), 24 (fixed + locked).

## Lesson: importlib-dataclass-sys-modules
Lesson ID: BL-20260527-importlib-dataclass-sys-modules
Scope: any CI test that loads a sibling Python module by file path via `importlib.util.spec_from_file_location(...)` when the sibling file defines `@dataclass`-decorated classes.
Problem Description: setUpClass fails with `AttributeError: 'NoneType' object has no attribute '__dict__'` at the moment the loaded module's `@dataclass` decorator runs. Stack trace points into `/usr/lib/python3.12/dataclasses.py:749` (`sys.modules.get(cls.__module__).__dict__`). The decorator needs to look up the owning module by name to resolve forward-reference annotations, but with `spec_from_file_location("_foo", path)` the module is not in `sys.modules` until it has finished executing — and the dataclass decorator runs DURING execution.
Root Cause: Python's `dataclasses` module assumes any class it decorates has already been registered in `sys.modules[cls.__module__]`. Standard `import` registers the module before executing the body. `importlib.util.spec_from_file_location` + `spec.loader.exec_module(mod)` does NOT — it executes first, then the test code is responsible for registering. So the moment Python hits an `@dataclass`-decorated class inside the loaded file, `sys.modules.get("_foo")` returns None, and `.<...>__dict__` raises AttributeError.
Solution: Register the module in `sys.modules` BEFORE `spec.loader.exec_module(mod)`:
```python
spec = importlib.util.spec_from_file_location("_foo", path)
mod = importlib.util.module_from_spec(spec)
sys.modules["_foo"] = mod          # <-- before exec
spec.loader.exec_module(mod)
```
This matches what `importlib.import_module` does internally. The same pattern is needed whenever the loaded module defines anything that introspects `sys.modules` during class body evaluation (dataclasses, typing.get_type_hints with forward refs, attrs, pydantic, etc.).
Constraints: Specific to CI tests that bridge "registered" and "manual" / file-path-only modules. The pattern recurs whenever a registered test exercises helpers from a module that is intentionally not on the import path (e.g. test/manual/ without __init__.py).
Validation Evidence: Round 25 AC-12 helper test (`test/registered/unit/manual/test_ac12_helpers.py`) hit this on first run with 11 ERROR results; all 11 turned PASSED after adding the `sys.modules["_ac12"] = mod` line before `exec_module`. The failing path was the `@dataclass _NIAHRunResult` definition inside `test/manual/test_double_sparsity_v32.py`.
Source Rounds: 25.

## Lesson: conservative-llm-output-parser
Lesson ID: BL-20260527-conservative-llm-output-parser
Scope: any test harness or eval that extracts a single-token answer (A-D, yes/no, JSON literal) from a free-form LLM response under temperature=0. Currently applied in `test/manual/test_double_sparsity_v32.py::_parse_mmlu_letter`; same pattern recurs in any future evaluator that reads short structured answers.
Problem Description: A naïve parser that "returns the first occurrence of an A-D character anywhere in the response" silently mis-scores common model completions. `"Answer: B"` returns `"A"` (the A in "Answer"). `"Awful but B is right"` returns `"A"` (the A in "Awful"). The defect is invisible without a counterexample test because most short A=A / B=B / C=C / D=D answers happen to coincide with the first A-D character. With `max_new_tokens` ≥ 4 (common for chat templates), the model frequently emits an answer-prefix and the parser converts every B/C/D answer into A silently. This pattern recurs across every LLM-eval harness Codex has reviewed in this loop.
Root Cause: LLM completions at `temperature=0` are NOT pure single-token answers — they contain answer-introducer prefixes, formatting punctuation, and explanation text. Scanning for "first occurrence of a valid answer character" ignores structure: the *position* and *boundary* of the character matters, not just its presence.
Solution: Two-tier conservative parser, regex-driven, with a hard fall-through to `None`:
```python
_LEADING = re.compile(r'^[\s\(\[\{<"\'`]*([A-Da-d])(?!\w)')
_MARKER  = re.compile(r'(?i)(?:answer\s*[:\-]?|answer\s+is|the\s+answer\s+is|option|choice)\s*[\(\[\{<"\'`:.]*\s*([A-Da-d])(?!\w)')

def parse(response):
    s = response.strip()
    if not s: return None
    m = _LEADING.match(s)
    if m: return m.group(1).upper()
    m = _MARKER.search(s)
    if m: return m.group(1).upper()
    return None
```
Critical details:
- `(?!\w)` after the captured letter forbids matching the first letter of a longer word like "Answer" / "Awful".
- Marker scan is case-insensitive (`(?i)`) so "answer is C" works alongside "Answer: B".
- Conservative: narrative text without a marker returns `None` rather than guessing.
- Unit tests must include the Codex-required counterexamples: `"Answer: B"`, lowercase `"b"`, `"(C)"`, `"D."`, narrative-no-marker, empty string.
Constraints: This is for "first valid token wins" eval patterns (MMLU, BoolQ, simple yes/no, etc.). For evaluations that need full structured output (JSON, multi-step reasoning), use a JSON parser or structured-output API instead.
Validation Evidence: Round 27 commit `faa41438e` — 13 registered regressions in `test_ac12_helpers.py` lock all of: `Answer:B→B`, `b→B`, `(C)→C`, `D.→D`, `[A]→A`, "answer is C"→C, "The answer is D."→D, "option B"→B, "Choice (A)"→A, narrative-no-marker→None, ""→None, whitespace-only→None, leading-punct→B. 271 unit tests pass total (was 254).
Source Rounds: 26 (introduced the broken first-char parser), 27 (fixed + locked).

## Lesson: dsv32-hf-calibration-load
Lesson ID: BL-20260528-dsv32-hf-calibration-load
Scope: calibrate.py, any code loading DeepSeek-V3.2 (model_type `deepseek_v32`) via HuggingFace transformers for an offline forward pass (calibration, eval harnesses).
Problem Description: `AutoModelForCausalLM.from_pretrained('/cluster-storage/models/deepseek-ai/DeepSeek-V3.2', trust_remote_code=True)` fails at `AutoConfig` with `ValueError: model type deepseek_v32 not recognized`. The checkpoint ships ONLY config.json + safetensors + tokenizer (no `auto_map`, no remote modeling .py), and transformers 5.8.1 has `deepseek_v3`/`deepseek_v4` but not `deepseek_v32`, so trust_remote_code has nothing to load. After remapping to `deepseek_v3` the model loads sharded FP8 across the GPUs, but the FORWARD then crashes: transformers' `finegrained_fp8.w8a8_fp8_matmul` fetches the `kernels-community/deep-gemm` hub kernel (a large cutlass JIT source tree) which (a) 429-rate-limits with 230s backoffs × 5 retries × many files, and (b) whose cached metadata.json uses an old schema (`version:1`, no `name`) that `kernels` 0.14.1 rejects with a `ValueError` — and `w8a8_fp8_matmul` only `except ImportError`, so the ValueError escapes and crashes the forward.
Root Cause: (1) V3.2 is served by SGLang's own model class, not registered with HF transformers; its config is an "unregistered model type". (2) transformers' deepseek_v3 FP8 inference is hub-kernel-dependent, and `_load_deepgemm_kernel` raises non-ImportError exceptions that transformers' fallback `except ImportError` does not catch. (3) Pile-val (`mit-han-lab/pile-val-backup`) ships zstd-compressed and `datasets` cannot read it without the `zstandard` package.
Solution: In calibrate.py: (a) `_resolve_calibration_config` reads the raw config via `PretrainedConfig.get_config_dict`; when `model_type=='deepseek_v32'` it builds a `deepseek_v3` config via `AutoConfig.for_model('deepseek_v3', **{...,'architectures':['DeepseekV3ForCausalLM']})` and loads FP8 weights under the transformers V3 MLA modeling (V3.2 = V3 + the DSA indexer, which is irrelevant to channel-importance calibration — only the MLA `kv_b_proj`/`q_b_proj` projections matter and are identical). Falls back to `AutoConfig.from_pretrained` when the raw config can't be read (unit fakes). (b) `_force_triton_fp8_for_calibration` replaces `transformers.integrations.finegrained_fp8._load_deepgemm_kernel` with a function that raises `ImportError` immediately (no fetch), so the forward uses transformers' own `finegrained-fp8` Triton fallback (small, loads cleanly online, numerically equivalent). Do NOT set `HF_HUB_OFFLINE=1` for the run — the Triton kernel's publisher-trust check needs the online API, and offline makes `lazy_load_kernel('finegrained-fp8')` raise "could not verify publisher trust status". (c) Make the one-block dry-run fail-closed (`_enforce_dry_run_placement`): on CUDA for an FP8 config, reject cpu/disk/meta placement, require multi-GPU sharding, and require float8 params present (catch a silent bf16 upcast) BEFORE the full run. (d) `pip install zstandard` to read Pile-val; a committed local `--dataset` corpus also works. (e) TOKENIZER-ONLY corollary (loop6 R16): when you need only the tokenizer for OFFLINE token counting (e.g. sizing a long-context probe payload or eval prompt to an exact token count), do NOT use `AutoTokenizer.from_pretrained(path, trust_remote_code=True)` — it resolves the unregistered `deepseek_v32` AutoConfig first and dies with the same `KeyError: 'deepseek_v32'` / `ValueError: ... model type deepseek_v32 ... not recognize`. The checkpoint ships `tokenizer.json`, so load it directly: `PreTrainedTokenizerFast(tokenizer_file=os.path.join(path,'tokenizer.json'))` (no config needed). Then VALIDATE the local count against the live server's authoritative `meta_info.prompt_tokens` from `/generate` (they should match exactly — R16's 70759-token AC-8 probe local-estimate == server prompt_tokens 70759).
Constraints: The deepseek_v3 remap is valid for channel-importance calibration ONLY (it ignores the V3.2 DSA indexer). Do not use this path to evaluate V3.2's sparse-attention behavior. Forcing the Triton FP8 path is a calibration-time choice (correctness over speed); production serving uses SGLang's own kernels and is unaffected. The tokenizer-direct-load corollary applies to any unregistered-model-type checkpoint that ships a `tokenizer.json`.
Validation Evidence: Round 1 hardware dry-run #5 (`runs/20260528_dsv32_mvp/calibrate_dryrun5_*.log`): V3.2 loaded FP8 sharded across all 8 H200s (dtype histogram float8_e4m3fn=604, no upcast), validator passed, Method-1 Q/K hooks fired on all 61 layers (H=128, head_dim=128). Full calibration wrote `/models/dsv32-fp8-channel-mask.safetensors` (content_sha256=7b3207cae888..., L=61 H=128 label_dim=16) validated by `load_channel_mask` (dtype=fp8_e4m3, page_size=64, channel_selection int32 (61,128,16), idx in [0,128)). 17 calibrate unit tests pass; commit `c99ed3644`.
Source Rounds: 0 (discovered the HF-load impossibility), 1 (remap + Triton fallback + fail-closed dry-run + mask generated/validated), loop6 R16 (tokenizer-only corollary: `PreTrainedTokenizerFast(tokenizer_file=...)` for offline token counting + server prompt_tokens cross-check).

## Lesson: dsv32-ds-serving-boot-chain

(6) the `double_sparsity`/radix-capture meta is skipped under CUDA-graph capture/replay (`_publish_ds_request_summary` host syncs are illegal during capture), so it only surfaces in eager mode.

Source Rounds: 2 (discovered + fixed the boot chain; decode-degeneration + meta-surfacing left open).

## Lesson: dsv32-ds-decode-degeneration
Lesson ID: BL-20260528-dsv32-ds-decode-degeneration

## Lesson: dsv32-ds-dense-prefill-sparse-decode
Lesson ID: BL-20260528-dsv32-ds-dense-prefill-sparse-decode

Problem Description: With DS enabled, any /generate request whose seq_len exceeds the dense-MHA prefill threshold (SGLANG_DSA_PREFILL_DENSE_ATTN_KV_LEN_THRESHOLD, ~2048) crashed the server with `CUDA error: an illegal memory access` (cls=bad_adapter_input, "N bad req_pool_indices in batch") in `_select_topk_indices` during prefill. Root Cause: Classic Double Sparsity is dense-prefill / sparse-decode by design (it sparsifies only the decode KV read; prefill attends densely — as the legacy SGLang DS did). Do NOT try to run DS selection during prefill — the eager scorer also materializes `[num_tokens, max_seq_len, H, label_dim]` (TBs for a long prompt). A proper per-token prefill selection kernel is only needed if DS-prefill sparsity is later wanted for AC-11 parity, which classic DS does not require.
Constraints: For prompts exceeding the chunk capacity, MHA_ONE_SHOT does not apply (sum_seq_lens > max_chunk_capacity) → falls back to the sparse path; that is the chunked-prefill (AC-1b) regime and needs separate handling. The fix keeps short-prompt behavior byte-identical and leaves non-DS (DSA) dispatch unchanged.

Scope: scheduler.py::get_internal_state, finalize_double_sparsity_bind (which stashes `server_args._*` runtime objects), any handler that serializes `vars(server_args)` over the ZMQ pyobj IPC; `/get_server_info` / `/server_info` HTTP endpoints.

## Lesson: ds-longcontext-needle-recall-vs-topk
Lesson ID: BL-20260529-ds-longcontext-needle-recall-vs-topk
Scope: any DS needle-in-haystack / long-context recall evaluation on DeepSeek-V3.2 (AC-1b chunked-prefill probe, AC-12 NIAH 4K/16K/64K); distinguishing a DS sparse-recall limit from a chunked-prefill / serving bug.
Problem Description: A DS chunked-prefill probe recalled an in-context needle exactly at ~10-12k tokens but returned a mangled answer ("OSPREME-3141" instead of "OSPREY-3141") at ~37k tokens — which could be misread as a chunked-prefill corruption.
Root Cause: DS sparse DECODE selects only `top_k` (=2048) KV tokens per step. A single needle sentence inside a ~37k-token context is one of ~37k tokens; its relevance signal does not reliably beat the other 35k, so the needle's KV is often NOT in the selected top-2048 and the model cannot attend to it precisely → degraded/garbled recall. This is an inherent DS sparsity tradeoff at long context, NOT a chunked-prefill or serving defect (the server prefilled in multiple 8192-token chunks and served without crashing; the numeric part was even right). It scales with context length: fine ≤~12k, degrades as context ≫ top_k.
Solution: When evaluating DS long-context recall, separate two questions: (1) does DS SERVE the long prompt (multi-chunk prefill, no crash, coherent) — a chunked-prefill/serving check; (2) does DS RECALL a specific needle — a sparse-selection check bounded by top_k. For (1), a multi-chunk prompt that serves coherently passes (AC-1b). For (2)/AC-12 NIAH at 16K/64K, expect recall to degrade as context grows past a few× top_k; if AC-12 NIAH gates fail at 64K, first check whether the needle could even be selected under top_k=2048 before treating it as a regression — it may be a documented sparsity limit, not a bug. Do not conflate the two.
Constraints: Applies to genuine sparse decode (seq ≫ top_k). At seq ≤ top_k DS selects all tokens (effectively dense) and recall is intact (see BL-20260528-dsv32-ds-decode-degeneration / the eager-meta lesson). A SECOND, independent long-context limit compounds with recall at the mem-0.6 operating point: DS reserves a per-rank TokenLabelTable, so its KV pool (`max_total_num_tokens`) is small — at mem 0.6 on V3.2/H200 it is only ~53K tokens (vs DSA at 0.85 ≈ 910K). A prompt longer than the DS pool is rejected with `HTTP 400: Input length (N) exceeds the maximum allowed` BEFORE any recall question applies. So a long-context AC-12 NIAH failure can be (a) a recall miss (needle not in top_k, server serves fine) OR (b) an admission failure (prompt > DS KV pool); distinguish them from the server log. Both are inherent to the DS operating point, not bugs.
Validation Evidence: loop5 R9 (qualitative) + loop5 R11 (AC-12 hard gate, quantified). R9: AC-1b radix-on probe: 10565-token prompt → multi-chunk prefill (8192+2432), served, needle "OSPREY-3141" recalled EXACTLY; ~37k variant served but mangled the needle word. R11 AC-12 paired DS-vs-DSA NIAH (chat transport, top_k=2048): DS recall degrades monotonically — 4K **75%** (15/20), 16K **5%** (1/20), 64K **unservable** (HTTP 400, 69970-tok prompt > DS pool 53056) — vs DSA (native long-context sparse attn) **100%** at every length. MMLU 5-shot (short prompts ≤ top_k) DS==DSA 89.00% → DS short-context quality intact. AC-12 recorded as HARD FAIL (the gate is hard pass/fail; DEC-7 directional handling is AC-11-only). `ac12_analysis.md`, `ac12_results/`, commit 1a1293f01.
Round-13 ADDENDUM — the budget is KERNEL-LOCKED and the gap is SELECTION QUALITY, not budget size: (1) You CANNOT raise DS `top_k` on V3.2 to widen recall — `top_k` must equal the model's native DSA `index_topk=2048`. The startup validator refuses a mismatch, and even with `SGLANG_DS_ALLOW_TOPK_MISMATCH=1` the `flashmla_kv` DECODE kernel asserts `indices.shape[-1] == self.dsa_index_topk` (`dsa_backend.py` `_forward_flashmla_kv`) during graph capture → DS reuses V3.2's native DSA decode kernel, which consumes exactly `index_topk` indices. (2) DS decode is SOUND: a DS-only NIAH sweep at top_k=2048 recalls **100%** at dense lengths (≤2048 tokens, budget≥seq), 75% at 4K (~50% selected), 5% at 16K (~12.5%) — recall tracks the SELECTED FRACTION, and is perfect when selection is complete. (3) Since DSA recalls 100% at the SAME 2048 budget + SAME kernel, the DS-vs-DSA gap is purely SELECTION QUALITY: V3.2's trained DSA indexer places the needle in its 2048; DS's offline Method-1 channel-mask does not. So on a model with a native trained sparse indexer, DS is capped at the native budget AND selects worse → it cannot match DSA long-context recall, and a larger top_k is not an available lever. `ac12_topk_sweep/analysis.md`, `ac12_topk_sweep/{ds_recall_vs_length_topk2048.json,boot_evidence_topk_locked.txt}`, commit 27434cee7.
Source Rounds: loop5 R9 (discovered/qualitative), loop5 R11 (AC-12 quantified + the mem-0.6 64K admission limit; hard-fail recorded), loop5 R13 (budget kernel-locked to index_topk; dense=100% proves decode sound; gap is selection quality vs the native DSA indexer).

## Lesson: ds-vs-dsa-memfraction-admission-asymmetry
Lesson ID: BL-20260529-ds-vs-dsa-memfraction-admission-asymmetry
Scope: any DS-vs-DSA serving/perf comparison on DeepSeek-V3.2 (AC-11 directional comparator); benchmark_compare.py cross-side server_args matching; interpreting DS TTFT under load.
Problem Description: The AC-11 comparator refused (exit 2) because DSA and DS server_args differed on mem_fraction_static (0.85 vs 0.6), random_seed (per-boot), and the DS-only double_sparsity_radix_fixture_artifact. Its cross-side check enforced FULL ServerArgs equality (minus only the DS-enablement pair), which is stricter than the plan's locked Option B set and impossible to satisfy: DS reserves a per-rank TokenLabelTable on top of ~84 GB/rank V3.2 FP8 weights, so DS must serve at mem 0.6 (0.7 OOMs during generation) while the baseline serves at ~0.85. When interpreting AC-11: a DS TTFT miss that coincides with DS achieved << nominal is admission-bound (a mem-0.6 KV-pool effect), not solely per-request latency; per DEC-7 it is a recorded directional follow-up, not a build-break.
Constraints: Do not silently absorb a locked Option B mismatch — only random_seed/mem_fraction are ignored, and the asymmetry is reported. The fix is for the DS-vs-DSA serving comparison; it does not change quality gates.

## Lesson: gate-record-artifact-before-raise
Lesson ID: BL-20260529-gate-record-artifact-before-raise
Scope: any paired hardware quality/eval gate harness that issues per-case server requests and must leave a durable per-case artifact (test/manual/test_double_sparsity_v32.py NIAH/MMLU; future DS gates). Applies to the request client (_generate) and the assert helper (_niah_assert) ordering.
Problem Description: A gate that (a) issues the measurement request with a RAISING client and (b) records the per-case artifact only AFTER the measurement call loses ALL durable evidence when the server REJECTS a case. AC-12 NIAH 64K: `_run_niah` called `_generate` (which raises `urllib.error.HTTPError` on a 400) and `_niah_assert` recorded the artifact only after `_run_niah` returned, so when DS rejected the ~70K-token prompt (prompt 69970 > mem-0.6 KV pool `max_total_num_tokens=53056`) the HTTPError escaped and `ac12_niah_65536_*.json` was never written. The pytest log proved the failure, but the structured per-gate artifact the contract required was missing and the evidence bundle overstated coverage. A reviewer (Codex) blocked task-completion on the missing artifact even though the underlying AC-12 verdict (hard fail) was not disputed.
Root Cause: Two coupled mistakes: (1) the generation call propagates a server rejection as an exception; (2) artifact recording is sequenced after the measurement instead of guaranteed before the assertion. A legitimate, recordable admission failure was thus handled like an infrastructure crash and skipped the evidence write.
Solution: Make the request path error-aware and record BEFORE asserting. (1) Wrap the client in an attempt shape (`_GenAttempt(text, ok, http_status, error, body)` via `_generate_attempt`) that catches `HTTPError`/`URLError` and returns a failed attempt carrying the HTTP status + response body, instead of raising. (2) Summarize per side (served count + first error); count an unservable case as a recall miss (text=""). (3) In the assert helper ALWAYS `_record_artifact(...)` (served counts, per-side error, `verdict`) BEFORE `assertTrue`, with a message that distinguishes a quality miss (recall delta) from an admission failure (server rejection). A server rejection is a recordable hard FAIL — never a silent skip nor an uncaught error. (4) Add a CPU regression that patches the client so one side raises `HTTPError` and asserts the gate fails cleanly (a failure, NOT an error) AND records exactly one artifact with the error details.
Constraints: Applies to hardware/integration gates where a server can legitimately reject an input (context-length limits, admission/OOM, rate limits). Keep the happy path byte-identical (the wrapper is transparent when ok=True) so passing cases and other lengths are unchanged. Pure-compute unit tests do not need this.
Validation Evidence: loop5 R11 (defect: 64K wrote no artifact, flagged by review as blocking #L) → R12 (fixed + locked). `test_niah_64k_ds_rejection_records_failure_artifact`: DS raises HTTPError(400) → 1 failure / 0 errors, exactly one niah_65536 artifact, `verdict=FAIL`, `ds_served=0`, DS error body present; 408 CPU tests pass. Hardware rerun produced `ac12_niah_65536_20260529T093912Z.json` (`dsa_served=20, dsa_hits=20, dsa_recall_pct=100.0`; `ds_served=0, verdict=FAIL`; `ds_error`=HTTP 400 "Input length (69970) exceeds the maximum allowed (53050)"). Commits d2f48bbd4, cc50bae38.
Source Rounds: loop5 R11 (introduced/flagged by review), loop5 R12 (fixed + locked).

## Lesson: sparse-gate-test-within-budget
Lesson ID: BL-20260529-sparse-gate-test-within-budget
Scope: designing quality/recall gates for a budget-limited sparse mechanism (Double Sparsity, native DSA, any top_k-bounded sparse attention) on a long-context model; AC-12 NIAH.
Problem Description: A gate that pass/fails a sparse-attention mechanism on needle recall at context lengths >> its selection budget tests it OUTSIDE its design envelope. DS selects a fixed top_k = the model's DSA index_topk = 2048 KV tokens per decode step (kernel-locked — see BL-20260529-ds-longcontext-needle-recall-vs-topk). A single needle in a 16K/64K context is information-theoretically unrecallable from a 2048-token selection, so the gate fails by construction — even though DS decode is correct (dense, seq ≤ budget → 100% recall = baseline) and the deficit is selection QUALITY vs the model's trained indexer, not a bug. Hard-failing such a gate conflates an inherent sparsity tradeoff with a defect and can stall a review loop indefinitely.
Root Cause: The gate's length points exceed the mechanism's selection budget, so it measures the sparsity tradeoff (which tokens get selected) rather than decode quality, and the budget cannot be raised to "cover" the needle without abandoning sparsity or building a new decode kernel.
Solution: Gate the sparse mechanism WITHIN its design envelope and CHARACTERIZE beyond it. HARD gates: (a) short-context quality parity (e.g. MMLU within N pp of the dense/native baseline), and (b) needle recall at context lengths whose tokenized length ≤ the selection budget (selection effectively dense) within M pp of the baseline. CHARACTERIZATION (recorded, NOT pass/failed against the baseline): recall-vs-length beyond the budget + any admission limit, with only a monotone-non-increase sanity assertion. Keep the beyond-budget artifacts' verdict=FAIL so the degradation stays transparent, never hidden. Any such re-scope of an immutable AC requires explicit owner authorization and a logged Plan Evolution; never silently relax a threshold or fake a pass. Add a CPU regression proving the within-budget hard gate still has teeth (a within-budget DS-miss must FAIL).
Constraints: Apply only when the out-of-envelope failure is proven inherent (decode sound at dense + the same-budget baseline succeeds — i.e. the gap is selection budget/quality, not a masked bug); rule that out first. The within-budget lengths must tokenize ≤ the budget (account for chat-template + tokenization overhead, so use word counts comfortably under the budget).
Validation Evidence: loop5 R14. User authorized the DS-fair re-scope (AskUserQuestion); re-scoped AC-12 PASSES on 8×H200 — MMLU 89%==89%, NIAH within-budget @1024/1536 words = 100%==100% (hard); beyond-budget 4K/16K/64K = 75%/5%/0% characterized (verdict=FAIL kept transparent). 411 CPU tests incl. a teeth-check that a within-budget DS miss FAILS and that a beyond-budget rejection is characterized without hard-failing. Commits 10f5b8878, a54a7364f; ac12_analysis.md, evidence_bundle.md.
Source Rounds: loop5 R14 (built on the R13 kernel-lock + selection-quality finding).

## Lesson: compact-sidecar-consumer-coverage
Lesson ID: BL-20260530-compact-sidecar-consumer-coverage
Scope: any quantized/compact tensor representation added behind a flag where a companion sidecar changes the SEMANTIC value of an existing tensor — e.g. the int8 Double Sparsity TokenLabelTable (`signatures` int8 + `scales` fp16, real label = `signatures * scales`). Consumers: selection_kernel scoring, radix_fixture_capture proof, validator radix fingerprint, channel_mask startup_sanity_probe, and any IPC/observability path that reads the base tensor.
Problem Description: After adding the int8 compact path, the scoring read path was threaded with `token_scales`, but every OTHER consumer still treated raw `signatures` as the authoritative label. Three concrete defects (a review reproduced the first): (1) `startup_sanity_probe` planted int8 values and scored WITHOUT `token_scales`, so it could PASS even when the real compact scorer (with scales) could not distinguish the planted needle — zeroing all scales kept the probe green while breaking real selection; (2) `radix_fixture_capture` hashed only signatures, so equal int8 bytes with different per-vector scales would false-MATCH the cold/warm label-stability proof; (3) the radix-fixture config fingerprint omitted `signature_dtype`, so an fp16-recorded artifact could authorize an int8 boot (different on-device label semantics) with the same mask/config surface.
Root Cause: a compaction sidecar changes the meaning of the base tensor (`signatures` alone → `signatures * scales`), but the sidecar was wired only into the hot read path. Proofs, fingerprints, self-tests, fixtures, and IPC that treat the base tensor as the value silently keep proving/authorizing on the pre-compaction representation — passing for the wrong reason.
Solution: when adding a compaction sidecar, enumerate EVERY consumer of the base tensor and thread the sidecar through each: (a) the scorer (first); (b) bit-stability proofs hash the sidecar per element alongside the base and add an explicit sidecar-divergence kind (`radix_fixture_capture` per-(layer,token) scale SHA + a `"scale"` divergence in `compare_cached_prefix`, including a compact-vs-default mode mismatch); (c) config fingerprints include the storage-mode field (`signature_dtype`) so a fixture recorded under one mode fails CLOSED under another (`for k in current: recorded.get(k) != current[k]` makes a missing key in an old artifact a mismatch automatically); (d) self-test/sanity probes plant SIDECAR-discriminative values (equal base magnitude, signal only in the sidecar) and score WITH the sidecar — so a probe that ignores it fails to find the needle, turning the probe into a real test of the compact path; snapshot/restore the sidecar too. Keep the default path's records byte-identical (sidecar keys appear only in compact mode) so existing proofs/fixtures stay backward-compatible. Add a regression that the self-test FAILS when the sidecar is zeroed/ignored.
Constraints: applies to any compact/quantized representation added behind a flag alongside a default representation (int4, page-level, etc.). The "enumerate every consumer of the base tensor" step is the load-bearing one — grep for every reader of the base buffer, not just the hot path.
Validation Evidence: loop6 R1 introduced the int8 path (scorer-only). loop6 R2: Codex review reproduced the `startup_sanity_probe` false-pass by zeroing all compact scales; fixed across validator.py (+`signature_dtype` fingerprint, fail-closed), radix_fixture_capture.py (per-(layer,token) scale SHA + `"scale"` divergence), dsa_backend.py (pass `table.scales`), channel_mask.py (scale-discriminative plant + `token_scales` + restore). 7 new regressions incl. the false-pass killer (`test_compact_scorer_requires_scales`, `test_compact_sanity_probe_finds_needle_and_restores_scales`) and the fp16-artifact-cannot-authorize-int8 fail-closed test; 279 DS unit tests pass. Commits 84d3410b9 (R1), e85cd2564 (R2).
Source Rounds: loop6 R1 (introduced the scorer-only compact path), loop6 R2 (review-found false-pass + fixed across all consumers).

## Lesson: verify-hardware-inventory-before-deferring
Lesson ID: BL-20260530-verify-hardware-before-deferring
Scope: any RLCR/hardware round where a step is declared infeasible or moved to "Explicitly Deferred" for a resource reason (GPU count, HBM, node access); the dev/serving box inventory assessment before a TP=N serve.
Problem Description: In loop6 R1 a `nvidia-smi -L | head -2` (output deliberately capped at 2 lines) was misread as "this box has 2 H200s", so the real-mask NIAH non-regression (needs TP=8 V3.2 serving, ~84 GB/rank × 8) was declared infeasible on the dev box and moved to "Explicitly Deferred" across R1→R2 with a confident justification. The box was actually **node 0 with 8 H200s** (full TP=8 feasible locally) plus a reachable node 1. Review (R2) rejected the deferral; R3 ran the NIAH on real hardware and it PASSED. The miscount cost a review cycle and produced a wrong tracker entry.
Root Cause: a self-imposed output cap on the inventory probe (`| head -2`) was treated as the inventory itself. A feasibility decision — and a plan-tracker deferral with a detailed "only 2 GPUs / 282 GB, can't fit 672 GB" justification — was built on the truncated view without re-running the probe uncapped.
Solution: before declaring a hardware step infeasible or deferring it, probe the FULL inventory and reason from it: `nvidia-smi --query-gpu=index,name,memory.total --format=csv` (count the rows), read `CLUSTER.md` for node topology/access, and confirm the fit (weights/rank × tp ≤ HBM/rank). Never let a display cap (`head -N`, `| head`) become the basis of a capacity claim. A "deferred for hardware" justification must cite the actual measured inventory. Corollary: a confident-sounding deferral is a red flag worth a 5-second re-check — the cost asymmetry is one cheap query vs a rejected deferral and a wasted round.
Constraints: applies to any feasibility/deferral decision gated on hardware capacity. Cheap to get right (one un-capped query); expensive to get wrong.
Validation Evidence: loop6 R1 (capped probe → believed 2 GPUs → deferred the NIAH), R2 (review rejected the deferral as plan-required), R3 (`nvidia-smi --query-gpu` showed 8 H200s on node 0; booted DS-int8 TP=8 on node 0 + live DSA on node 1; real-mask NIAH PASS — int8 DS recall ≥ fp16 at every length; commit 8a05b1688).
Source Rounds: loop6 R1 (introduced the miscount + wrong deferral), loop6 R3 (full probe corrected it; ran the real serve).

## Lesson: footprint-reduced-memfraction-ceiling-is-cudagraph-capture
Lesson ID: BL-20260530-int8-memfraction-ceiling-is-cudagraph-capture
Scope: DS mem-fraction lift on V3.2 (AC-4) and any footprint-reduced sparse-attention serve where mem_fraction_static is swept toward a target; `serve_double_sparsity.sh`; interpreting a high-mem-fraction OOM.
Problem Description: After the int8 footprint reduction relieved fp16's `mem_fraction_static=0.7` *generation*-OOM (int8 at 0.7 serves a sustained 4096-ISL × conc-32 load with no gen-OOM), pushing to the nominal `0.8` target still OOM'd — but the OOM was a **boot-time CUDA-graph-capture failure** (`Capture cuda graph failed: ... Tried to allocate 146 MiB ... 132 MiB free`), NOT a generation-time OOM and NOT "the table is still too big". At 0.8 the int8 table (12.10 GB) + the 739K-token KV pool (33 GB) leave only ~22.7 GB pool-end headroom, and the fixed ~11.6 GB cuda-graph capture pool (52 Option-B batch sizes) does not co-fit with the table.
Root Cause: once the footprint lever frees enough *generation* headroom, the binding HBM constraint at high mem_fraction MOVES from generation-activation headroom to the BOOT-time cuda-graph capture pool (a fixed cost), which competes with the table + the now-much-larger KV pool. The achievable mem-fraction ceiling is therefore set at boot (cuda-graph capture), not at generation.
Solution: do NOT read a high-mem-fraction cuda-graph-capture OOM as "the footprint lever is insufficient → escalate to the structural/page-level lever". Check the admission target first: at 0.7, `max_total_num_tokens=396096` is ~3.5× the conc-64 admission requirement (~114K from the AC-2 budget), so the admission goal is already met and a higher fraction is unnecessary. Define the operating point as "the highest fraction that BOOTS (cuda-graph capture fits) AND survives a sustained generate", and target admitted KV capacity, not the mem-fraction number. Reaching a higher fraction would require trimming the fixed cuda-graph batch set — a change to the locked Option-B config, out of scope unless the admission target is genuinely unmet.
Constraints: applies to V3.2 TP=8 / similar large MoE with a fixed multi-batch cuda-graph capture set; the exact ceiling depends on weights + cuda-graph pool + table + KV pool and must be re-measured per model. Distinguish a boot-time cuda-graph-capture OOM (this) from a generation-time OOM (the AC-4 negative test) — they have different remedies.
Validation Evidence: loop6 R4. int8 sweep on 8×H200 TP=8: 0.6 (table 0.87 GB, max_total 53056) and 0.7 (table 6.48 GB, max_total 396096) serve; 0.7 survives a sustained 32-conc 4096-ISL generate (97/97 OK, no gen-OOM, NVML plateau) where fp16 0.7 gen-OOM'd in Loop-5; 0.8 (table 12.10 GB, KV 33.09 GB) boot-OOMs in cuda-graph capture. `runs/20260530_dsv32_loop6/memfraction_sweep_int8.md`, commit 75e68053f.
Source Rounds: loop6 R4.

## Lesson: durable-tracked-acceptance-evidence
Lesson ID: BL-20260530-durable-tracked-acceptance-evidence
Scope: any RLCR hardware-AC acceptance artifact under `runs/`; the evidence-bundling step for a hardware claim (mem-fraction sweep, benchmark, NIAH, no-OOM proof).
Problem Description: The Round-4 AC-4 artifact *summarized* the no-OOM result ("97/97, plateau") and *referenced* `nvml_timeseries_0.7.csv`, but `*.csv` is gitignored in this repo, so the time series never committed; there was also no tracked client request/result log or server-log excerpt. Review rejected AC-4 as not durably verifiable even though the underlying run passed. Separately, the "full HBM budget" reported NVML + the big named tensors but not the torch reserved/allocated residual / named-small components the AC required.
Root Cause: (1) evidence was referenced/summarized rather than EMBEDDED as TRACKED files, and the chosen format (`.csv`) matched a `.gitignore` pattern so it silently did not commit. (2) "full HBM budget incl. torch residual" was read as "list the big named tensors" rather than "a budget that CLOSES" (named + residual = total).
Solution: (a) embed/track acceptance evidence as committed `.txt`/`.md`/`.json`, NOT formats the repo ignores (`.csv`/`.log`/`.jsonl` here); confirm with `git ls-files`/`git status --ignored` on the bundle and run `git diff --check` to catch trailing whitespace before claiming done. (b) For a "full HBM budget", CLOSE it: derive every named component from the server's own torch memory stage-deltas (SGLang logs `avail mem` / `mem usage` at torch-init / `Load weight end` / KV-cache / `Capture cuda graph`), report `torch_used = total − avail` and NVML used (== per-process when the server is the sole GPU process, verifiable via `nvidia-smi --query-compute-apps`), plus a labeled residual bucket = `NVML_used − Σnamed`; the sum must ≈ total (~0.5 GiB driver reserve). A boot OOM message also prints literal torch allocated/reserved for free. (c) For a benchmark percentile claim, commit the EXACT numeric source (per-request arrays + the bulky per-token array when a published percentile needs it — do NOT publish a metric, e.g. ITL, whose exact source you did not commit) plus a recompute script + the source-file SHA256. (d) A recompute/verify script must be FAIL-CLOSED: `raise SystemExit(1)` on any mismatch and add sanity checks (counts, array lengths, all-empty/expected-constant fields) — a verifier that prints "FAIL" but exits 0 is just a readable report and a reviewer WILL mutate a copy to test it (Codex did, and the fail-open script returned 0). Demonstrate fail-closure by mutating a copy and showing exit 1. The fail-closed comparison TOLERANCE must be ≤ the PUBLISHED precision (loop6 R14 used `TOL=0.05` against a 3-decimal report → a value rendering 46.973 vs the published 46.983 still passed; R15 tightened to ≤0.0005), and the verifier must VALIDATE the provenance/shape fields it relies on — full 64-hex SHA256 (a `deadbeef` SHA passed until checked), required scalars numeric, array length == completed — not only recompute the metric. (e) When the published number comes from a downstream CONSUMER (e.g. `benchmark_compare.py`), the recomputable source must store the EXACT field/formula the consumer uses and the verifier must recompute the consumer's PUBLISHED value — not an adjacent-looking field. loop6 R13: the AC-7 metrics JSON stored `max_concurrency` (the nominal cap, 64) as "achieved", but the comparator's achieved-concurrency is the JSONL `concurrency` field (effective, 46.983); the "recomputable source" silently could not reproduce the headline. Fix (R14): store the effective `concurrency` + recompute the comparator's medians and assert == the published `ac11_resweep.md` rows.
Constraints: applies to any hardware AC where the durable artifact IS the acceptance evidence. ## Lesson: admission-restore-trades-per-request-tps-for-ttft
Lesson ID: BL-20260530-admission-restore-tps-tradeoff
Scope: any DS / sparse-attention serving where a footprint/pool change restores KV admission to raise concurrency on a large MoE (V3.2 AC-4/AC-5); interpreting a per-request TPS SLO measured at a queue-starved vs a restored-admission operating point.
Problem Description: The loop premise was "DS already beats the >=30 TPS/req SLO (Loop-5 measured 34.0/33.9/33.9), the only blocker is TTFT/admission." But that 34 TPS was measured at the QUEUE-STARVED operating point (mem-0.6, 53K KV pool admitted only ~2-3 of the 4608-token requests into decode at conc 64 -> tiny decode batch -> 34 tok/s/req). Root Cause: a batched decode advances EVERY in-flight request one token per forward step, so per-request decode TPS ~= 1/decode_step_time, and decode_step_time grows with the running batch (MoE + attention compute). The per-request TPS measured at a queue-starved operating point (few concurrently decoding) is NOT the TPS at the restored-admission operating point (many decoding); conflating them hides a real latency/throughput tradeoff.

The ">=30 TPS/req AND high concurrency" combo may be in genuine tension on a large MoE; the remedy is decode optimization or an explicit admission/throughput operating-point choice, not more footprint reduction. Always pair the TTFT result with (a) the per-request TPS at the same operating point and (b) the admission-wait-vs-prefill-compute attribution (queue_duration vs forward_duration), so a TTFT win that hides a TPS regression is caught.
Constraints: V3.2 671B MoE TP=8; the exact batch->TPS curve is model/hardware-specific. The tradeoff DIRECTION (more admitted concurrency -> lower per-request TPS) is general to batched decode.

## Lesson: cold-flood-run-is-not-a-steady-state-slo
Lesson ID: BL-20260530-cold-flood-not-steady-state-slo
Scope: any client-SLO confirmation via `bench_serving` / `benchmark*.sh` with `WARMUP_SECONDS=0` (or a short window) at `request_rate=inf` + a `max_concurrency` cap; reading TTFT/TPS from such a run; AC-6-style "default meets the SLO unchanged" proofs.
Problem Description: A quick AC-6 DSA-default SLO confirmation (`WARMUP=0`, `WINDOW=30`, `NUM_PROMPTS=64`, conc 16/32/64) reported DSA P99 TTFT 22.5 s and per-req TPS 16.9 at conc 16 — wildly worse than the established Loop-5 DSA steady-state baseline (0.73 s, >=30 TPS) at the SAME operating point. Taken at face value it would falsely say "DSA misses the SLO."
Root Cause: `request_rate=inf` + a `max_concurrency` cap floods the first epoch — all N prompts are released and `max_concurrency` of them prefill simultaneously (e.g. 16x4096 tokens), so time-to-first-token is dominated by prefill/decode CONTENTION during the cold ramp, and per-req TPS by the large concurrent decode batch. With `WARMUP=0` the measurement window captures exactly this ramp, not the staggered steady state a 120 s-warmup / 600 s-window run reaches (where arrivals are spread and each prefill is mostly uncontended). The inflation is a property of the MEASUREMENT (cold flood), not of the attention variant.
Solution: do NOT report TTFT/TPS from a cold-flood as a steady-state SLO number. Use it only to confirm ADMISSION (achieved concurrency == nominal) and clean SERVING (errors 0). For the SLO latency/throughput claim, ensure the run actually reaches steady state. **Two distinct cold-ramp traps, both seen:** (1) `WARMUP=0` — the window is the ramp. (2) **`WARMUP>0` but the EPOCH is longer than the warmup** — with `request_rate=inf`, bench_serving processes `num_prompts` per epoch; if `num_prompts` is large the epoch wall-clock (≈ num_prompts/concurrency × per-request time) exceeds the warmup, so the measurement starts mid-first-epoch and still captures the synchronized burst. R11: `num_prompts=320` at conc-16 → epoch ≈ 558 s ≫ 120 s warmup → DSA P99 TTFT 17.2/34.2 s (cold-ramp); `num_prompts=64` → epoch ≈ 35 s ≪ 120 s warmup → DSA 0.89/1.49/2.18 s (steady state, reproducing the Loop-5 baseline 0.97/1.39/2.02 s). **Rule: pick `num_prompts` so the epoch ≪ warmup (small num_prompts cycles many times within the warmup), or use the established small-`num_prompts` baseline.** A strong tell of a ramp artifact: a tight median≈p99 well above a small `min`. Cross-check the NATIVE baseline under the same methodology (under `WARMUP=0`, DSA 22.5 s was not better than DS's AC-5 12.8 s — confirms cold-ramp, not DS-specific).
Constraints: applies to flood-style `request_rate=inf` benches; an open-loop Poisson `request_rate` run has a different (load-dependent) profile. Steady-state numbers are operating-point-specific.
Validation Evidence: loop6 R10/R11. R10 `WARMUP=0` (trap 1) and R11 `NUM_PROMPTS=320`/120 s-warmup (trap 2) both read DSA cold-ramp TTFT (22.5 / 17.2-34.2 s); R11 `num_prompts=64` reproduced the steady-state baseline (`dsa_default_slo_np64.txt`: 0.89/1.49/2.18 s, <22) which matches the tracked Loop-5 DSA baseline (`dsa_default_matches_loop5_baseline.txt`, byte-identical operating point). `runs/20260530_dsv32_loop6/ac6_optin_dsa_default_product.md`.
Source Rounds: loop6 R10 (WARMUP=0 trap), R11 (epoch>warmup trap + the num_prompts=64 fix).

## Lesson: launching-a-persistent-remote-server-over-ssh
Lesson ID: BL-20260530-remote-server-launch
Scope: starting a long-lived SGLang server on the remote node (node 1) over `ssh double-sparsity` for a cross-node DS-vs-DSA run; any "boot a detached server on another node" step.
Problem Description: In loop6 R13 the node-1 DSA server would not stay up across ~6 attempts (setsid, nohup, tmux new-session), each leaving an EMPTY log + no `launch_server` proc + GPU at 0 MiB. ~2h lost before pivoting to run both servers on node 0 sequentially. Failure modes hit, in order: (a) `ssh node1 'setsid bash -c "serve.sh ..." & echo'` — when the ssh channel closes fast the forked process is torn down before it establishes (the "parent exits too fast" no-op); (b) `bash development/serve_native_nsa.sh` (RELATIVE path) — remote login cwd is `/root`, not the repo, so the script is "No such file" and nothing launches; (c) `tmux new-session -d -s dsa "ENV=.. bash .. > log 2>&1"` — tmux does NOT run a full shell for the command arg, so env-vars + the `>` redirect aren't interpreted and the session exits instantly; (d) `pgrep -f "python3 -m sglang.launch_server"` FALSE-matched my own ssh command text, giving phantom "PROC_UP" reads (use `ps -eo pid,stat,cmd | grep "[s]glang.launch_server"` with the bracket trick instead).
Root Cause: ssh-launched background processes are fragile across channel close; tmux command args bypass the shell; remote cwd ≠ repo; pgrep -f matches the launcher's own command line.
Solution: prefer the simplest reliable path. (1) If cross-node is not essential, run both servers on the LOCAL node SEQUENTIALLY (node 0 boots via the Bash `run_in_background` tool are reliable and persist) — this is comparator-clean (same session/commit; only per-side mem differs). (2) If a remote server is needed, use `tmux new-session -d -s NAME` then `tmux send-keys -t NAME "cd /REPO && ENV=.. bash ABSOLUTE/serve.sh > log 2>&1" Enter` (send-keys types into the session's interactive bash, which handles cd/env/redirect) — and verify with `ps | grep "[s]glang.launch_server"` + GPU climbing, NOT pgrep -f. (3) ALWAYS use the ABSOLUTE script path remotely (login cwd is /root). (4) In harness Bash, `pkill` returning 1 (no match) trips `set -e` — use `pkill ... || true` (a trailing `; true` does NOT guard set-e); and foreground `sleep` is blocked — never chain `sleep` in a multi-step Bash call.
Constraints: cluster-specific (2-node H200, ssh double-sparsity); the "run both on node 0 sequentially" fallback doubles wall-clock but is reliable.
Validation Evidence: loop6 R13 — node-1 DSA boot failed via setsid/nohup/tmux-arg (empty logs, GPU 0); ran AC-7's DS+DSA both on node 0 localhost sequentially → 18 clean runs, comparator-clean. commit 5e6d3afb5; `runs/20260530_dsv32_loop6/ac7_resweep/ac11_analysis.md` methodology note.

## Lesson: clean-per-conc-latency-attribution
Lesson ID: BL-20260530-clean-latency-attribution
Scope: any latency-SLO acceptance that attributes a tail metric (TTFT) into components from a server request-time-stat log (`ReqTimeStats.queue_duration` / `forward_duration`) under continuous batching; the attribution step of a benchmark AC.

Root Cause: treating a server-side counter log as clean/aligned with client metrics without (a) disclosing a filtering policy for impossible rows, (b) reconciling row counts against the nominal request count, (c) checking what each counter actually measures, or (d) respecting that per-percentile rows across two distributions are different requests so their percentiles cannot be subtracted.
Solution: (a) parse the FULL log and CLASSIFY rows before counting — separate health-check probes, warmup/readiness rows, and the actual benchmark rows by a stable shape signature (here `output_len=512` marks the 320-token-budget client requests; warmup rows are `output_len` 8/32). Report the reconciliation total = health + warmup + benchmark, drop impossible rows (`queue_duration<0`) with the count + a one-line policy, and reconcile valid-vs-nominal EXACTLY (do not hand-wave "valid>nominal is warmup" — that produced the false `959>960` claim; the truth was 960 benchmark rows, 5 invalid, 955 valid). (b) State measured-vs-inferred explicitly: `queue_duration`=admission wait (MEASURED), client TTFT=authoritative (MEASURED), min(TTFT)=uncontended prefill floor; post-admission residual=`TTFT_p99−queue_p99` is INFERRED (prefill PLUS chunked-prefill/decode interleave, not pure prefill). (c) Never use a completion-time counter (`forward_duration`) as a first-token term — "context only". (d) Compare tail-to-tail (p99 vs p99), not p50−p50 across two distributions. (e) Group per-conc by a RELIABLE key: when runs are sequential, use **request-completion print-time** (the log line's `[HH:MM:SS]` prefix) split at the largest gaps — NOT `entry_time` gaps and NOT `T0+cumulative-durations` (entry_time has within-run waves that rival inter-run gaps, and a T0 anchored on readiness/warmup mis-buckets; both were tried and failed). Validate the grouping reproduces the benchmark's known per-conc completion count. (f) If a root cause cites decode-batch growth, attach the tracked decode-batch excerpt with per-#running-req gen throughput so per-req TPS = gen/#running-req is recomputable. (g) For the metric percentiles, commit the EXACT per-request arrays (or a checksum + a recompute script) so a reviewer recomputes from committed files, not summary-vs-summary.
Constraints: applies wherever a server counter log backs a latency-attribution claim; percentile-subtraction across distributions is only an upper-bound heuristic, tail-to-tail is the defensible statement; row-count reconciliation must be exact arithmetic, not a narrative.

## Lesson: ds-decode-selection-overscans-full-context
Lesson ID: BL-20260531-ds-selection-fullwidth-overscan
Scope: DeepSeek-V3.2 Double Sparsity DECODE selection on the graph-safe path — `selection_kernel.py::_logical_score_kernel` / `retrieve_topk_graph_safe`, `cuda_graph.py::allocate_graph_state`, `dsa_backend.py` (the two `allocate_graph_state(..., max_seq_len=int(self.req_to_token.shape[1]))` sites); any per-decode-step sparse selection whose scan width is the KV-index buffer width rather than the actual sequence length.

FlashMLA decode uses the batch-max actual seq (`max_seq_len_k`); the DS selection alone over-scanned to full context.

The launch grid is unchanged (graph-capture-safe; no host sync, no dynamic shape), only per-program work shrinks; output is bit-identical (those positions were already -inf), so NO flag and NO recall/correctness change. It does NOT cap context (preserves 64K servability) because each program still scans up to its OWN seq_len. Profile-first method that found it: (a) CLOSED-batch (N parallel /generate, ignore_eos, no new arrivals) gives pure per-request decode TPS = server `gen throughput / #running-req` with `#queue-req:0`, isolating decode from prefill-interleave; (b) a standalone GPU microbench of `retrieve_topk_graph_safe` swept across scan widths attributes selection vs topk and quantifies the over-scan. Constraints: applies to per-decode-step sparse selection on a graph-captured path where the scan width defaults to the KV-index buffer (context) width. The early-exit is safe only for token-blocks ENTIRELY past seq_len (partial boundary blocks fall through to the normal per-position mask). Do not cap `max_seq_len`/context to "fix" this — that trades away long-context servability; fix the kernel to do work proportional to actual seq instead.
Validation Evidence: loop6 R17 on 8xH200 TP=8 (DS int8 / mem 0.7 / radix-on). `verify_early_exit.py`: selection identical at width 4608 vs 163840 for layers 0/7/30/60; selection @163840 32.08 -> 12.50 ms/step. 281 DS unit tests pass. Source Rounds: loop6 R17 (profiled the decode hot path, localized the full-context over-scan, fixed the score kernel; topk over-scan left as the next lever), R18 (topk residual is capture-width-bound → bounded-context operating point clears conc-16 >=30; conc-32/64 characterized as the structural decode-batch ceiling DS ≤ DSA; owner set AC-5 done-criterion = conc-16 strict + characterize 32/64). R24 — DECISIVE: there is NO graph-safe FULL-CONTEXT blocked-top-k design that reduces the residual merge over-scan / reaches conc-16 >=30. Lesson: before building a research-grade graph-safe top-k kernel, MICROBENCH the candidate widths — a 2-stage blocked top-k under fixed graph shapes is not automatically faster than one monolithic topk. ## Lesson: topk-selector-equivalence-needs-deterministic-tiebreak
Lesson ID: BL-20260531-topk-deterministic-tiebreak
Scope: any DS top-k selector that has MULTIPLE implementations expected to agree — `selection_kernel.py::select_topk_sequence_order` (monolithic torch.topk), `blocked_topk_sequence_order` (the blocked oracle/eager fallback), and the future graph-safe Triton blocked top-k; any time an "exact oracle" is asserted bit-identical to another selection implementation.
Problem Description: A blocked top-k built as an "exact oracle" for a future kernel used `torch.topk(..., sorted=False)` per block + `torch.topk` for the merge, and its tests asserted exact tensor equality against the monolithic `select_topk_sequence_order` — but only on DISTINCT random scores. On FINITE TIES the two diverged (Codex counterexample: all-ones scores, K=3, block_width=4 → monolithic [4,5,6] vs blocked [4,6,7]). DS scores tie in practice (int8/scaled scoring, masked/repeated values), so the "identical oracle" claim was false and a kernel written against it could match the oracle while diverging from the production monolithic path on real tied scores.
Root Cause: `torch.topk` (and an unspecified argsort) break score ties ARBITRARILY/implementation-defined, and that arbitrary order differs between a whole-array topk and a per-block-then-merge topk. Two "correct" top-k implementations that select the same SET on distinct scores select DIFFERENT positions at a tie boundary unless they share an explicit deterministic tie-break.
Solution: define ONE deterministic ordering for all DS top-k selectors — (score DESCENDING, then logical position ASCENDING) — and implement it via a shared helper. Concretely `_topk_by_score_then_pos(vals, pos, k)`: (1) `argsort(pos, stable=True)` to put candidates in ascending-position order, then (2) `argsort(vals, descending=True, stable=True)[:, :k]` so equal values resolve toward the lower position (stable sort preserves the position-ascending order among ties). The monolithic selector feeds `pos = arange(n)` (already ascending); the blocked selector feeds the gathered candidate (val, global-pos) pairs. With this shared contract the blocked path is bit-identical to monolithic INCLUDING on ties, and any future kernel written against the oracle inherits the same tie-break. Test ties explicitly: all-equal scores, ties crossing block boundaries, ties exactly at the K boundary, ties mixed with -inf padding (distinct-score tests do NOT exercise the divergence). Use fresh argsort outputs (no in/out aliasing — BL-20260527-torch-topk-aliasing-corrupts-input).
Constraints: applies whenever ≥2 implementations of the same top-k/selection must agree, or an oracle is asserted identical to another. The deterministic tie-break is quality-neutral for DS (equal-score tokens are interchangeable) but is required for cross-implementation equivalence + reproducibility. A stable sort is needed (PyTorch `stable=True`); plain `torch.topk`/`torch.sort` are not stable.
Validation Evidence: loop6 R22 (introduced the blocked oracle with arbitrary ties; Codex found the all-ones counterexample), R23 (shared `_topk_by_score_then_pos`, both selectors bit-identical incl. ties; 4 finite-tie regressions added — all-equal/cross-block/at-K/with-inf; 289 DS unit tests pass; the all-ones K=3/bw=4 case now [0,1,2] in both). commit 2715b7382.
Source Rounds: loop6 R22 (defect surfaced by review), R23 (deterministic shared tie-break + finite-tie regressions).

Problem Description: Assembling the DS-vs-DSA served-recall matrix (N=20), a naive symmetric materiality test (`hybrid_recall outside the DS-default 95% CI`, i.e. `h > base_hi OR h < base_lo`) flagged the 64K cell as a "material" change: DS-default 1/20=5% has Clopper-Pearson CI [0.1%, 24.9%], and DS-hybrid 0/20=0% is technically just below the 0.1% lower bound, so a ONE-needle move (1 hit vs 0 hits) was reported as a material regression. For real regression claims at small N, require the two CIs to be disjoint AND the gap to exceed a couple of needles, or raise N. Always print the raw hits/served next to the percentage so a reader sees the needle counts behind a "5% vs 0%".
Constraints: applies to small-N (≤~30) binomial recall/accuracy gates. At larger N the floor CI tightens and the artifact disappears, but the directional-uplift rule is still the correct reading of "delta exceeds the baseline CI". Within-budget parity and material UPLIFTS (e.g. 16K 5%→40%, 40% > CI-hi 24.9%) are unaffected — those are genuine.

## Lesson: tensorize-per-row-eviction-for-graph-safe
Lesson ID: BL-20260602-tensorize-per-row-eviction-for-graph-safe
Scope: porting any per-row Python decode-path loop (eviction / force-include / scatter with `.item()` + a `for b in range(bs)` body) to a CUDA-graph-safe tensor op — `selection_kernel.py::_force_include_anchor` (anchor-budget force-include) and any future post-topK / per-request selection mutation that must run under graph capture.
Problem Description: The anchor-budget force-include was a per-row Python loop (`for b in range(bs)`, `.item()`, Python `set`/`list.sort`), so a non-default `anchor_mode` forced the eager selector and was rejected under CUDA graph — leaving the third AC-3 variant production-unviable. It had to become graph-safe (fixed shape, no host sync, alloc-free under replay) AND stay bit-identical to the existing eager semantics (which several unit tests pin exactly), including the R3 over-budget clamp `effective_budget=min(budget,valid_count,seq_len)` and strided's `sorted(set(...))` dedup.
Root Cause: per-row loops with `.item()` host syncs and dynamic Python data structures cannot be captured in a CUDA graph (illegal host sync during capture; variable shapes). A naive tensorization also silently diverges from the eager path on ties/edge cases (the eager `list.sort(key=score)` is STABLE → position-ascending tie-break; strided dedups by value; eviction is bounded to the already-selected set, not a re-topk over full scores).
Solution: tensorize the WHOLE operation, fixed-shape, no `.item()`: (1) compute per-request anchor positions as `[bs, A]` + a validity mask (recency/global/strided arithmetic from seq_len; strided dedup = mark slot invalid when its value equals the previous slot's, since strided values are ascending in i); (2) build `[bs, max_seq]` membership masks via `scatter_` (an extra sentinel column absorbs `-1` pads) to test "anchor already selected?" / "selected is an anchor?"; (3) evict the k lowest-score non-anchor selected by ranking with a deterministic (score-asc, position-asc) order — two stable `argsort` passes (`argsort(pos, stable)` then `argsort(score, stable)`) reproduce the stable Python `list.sort` tie-break exactly; (4) insert the first k missing anchors via `cumsum` rank; (5) combine keep+insert positions, `torch.sort` ascending, pad to K. CRITICAL: FUZZ the tensor version bit-identical against the OLD per-row reference (thousands of random `n/K/budget/mode` incl. over-budget + tiny seq_len) BEFORE swapping it in, then use the SAME function in both the eager and graph-safe paths so they cannot diverge. Under CUDA-graph capture the extra ops (scatter/sort/argsort) are captured once and replay reuses their memory (alloc-free on replay) — prove it with a real `torch.cuda.CUDAGraph` capture + `assert_no_alloc_in_region(replay)`, not just the allocation-free-eager pattern.
Constraints: the `[bs, max_seq]` masks are O(bs·max_seq) memory (fine: ~MBs at 160K), NOT O(max_seq²) — never rank by an all-pairs comparison over max_seq. Operate on the already-selected K positions (K≤2048) for the eviction ranking, not the full score width. A stable sort is required (`torch.argsort(..., stable=True)`); plain argsort is not stable. Keep the deterministic tie-break shared with the top-k selectors (BL-20260531-topk-deterministic-tiebreak).

## Lesson: flash-mla-sparse-fwd-compact-decode-contract
Lesson ID: BL-20260602-flash-mla-sparse-fwd-compact-decode-contract
Scope: the opt-in lifted-budget DS decode path that routes a wider-than-`index_topk` selection through `flash_mla_sparse_fwd` instead of `flashmla_kv` — `double_sparsity/lifted_budget.py::build_compact_decode_index`, the decode-branch wiring in `dsa_backend.py` (`_forward_flashmla_sparse` + the `dequantize_k_cache_paged` call), and any future consumer that feeds `flash_mla_sparse_fwd` for an fp8 KV op-point.
Problem Description: For the fp8 DeepSeek-V3.2 op-point the default DS decode uses `flashmla_kv` (asserts `indices.shape[-1] == dsa_index_topk == 2048`). To attend a wider budget you must instead use `flash_mla_sparse_fwd`, but (a) that kernel is the BF16 backend (`bfloat16 ↔ flashmla_sparse` in the validator) so the fp8 KV must be dequantized first via `dequantize_k_cache_paged`, which returns a COMPACT `[total_valid,1,576]` bf16 tensor keyed by `page_table_1_flattened` — so `flash_mla_sparse_fwd` needs COMPACT-domain (request-local ordinal) indices, NOT physical KV slots; and (b) two non-obvious kernel ABI requirements bite if you pass naive indices: a `width=8` index tensor crashes with `Assertion params.topk % (2*B_TOPK) == 0` (csrc/sm90/.../phase1.cuh), and pad/over-budget lanes must be marked so the kernel masks them.
Root Cause: `flash_mla_sparse_fwd` is a block-tiled sparse-attention kernel: its `topk` (last index dim) must be a multiple of the kernel block `2*B_TOPK` (= 128 here), and it masks a query→key pair iff the index is `< 0` OR `>= s_kv` (the kv length). The compact buffer's rows are ordinals `0..total_valid-1`, so a physical slot value would either be out of range (silently masked) or point at the wrong compact row; and the same physical slot shared across requests (prefix sharing) must map to each request's OWN compact span or attention cross-contaminates.
Solution: build a request-local compact remap (`build_compact_decode_index`): (1) `page_table_1_flattened` = the concatenation of each request's VALID physical slots in selector order, with NO `-1` (it is the literal input `dequantize_k_cache_paged` loads — a `-1` there is an illegal load); (2) compact indices = `request_base[i] + rank_within_request` (request_base = exclusive cumsum of per-request valid counts), so each request attends only its own dequant span (prefix-sharing-safe); (3) pad lanes = `-1` (the kernel masks `<0`/`>=s_kv`, so no safe-placeholder is needed in the COMPACT domain); (4) collapse within-row duplicates to the highest selection rank (a stable value-sort + first-of-run keep), since `flash_mla_sparse_fwd` would double-attend a duplicated valid index; (5) make the padded width (`lifted_budget_top_k`) a multiple of 128 — the config/validator must enforce `lifted_budget_top_k % 128 == 0` (4096/8192 satisfy it). PROVE the kernel half directly: a >2048-wide (e.g. 3000@4096-budget) `flash_mla_sparse_fwd` vs a reference attention (no-cap), and a full fp8→`dequantize_k_cache_paged`→`flash_mla_sparse_fwd` pipe with prefix sharing vs a reference attending the dequantized selected slots (compact rows must be bit-identical to the full-dequant gather). The internally-allocating `dequantize_k_cache_paged` is NOT graph-safe, so the research path runs eager (`--disable-cuda-graph`) until an `out=`/scratch variant lands.
Graph-safety corollary (R16): the eager `build_compact_decode_index` above produces a `page_table_1_flattened` whose length is `total_valid` — which VARIES per decode step, so the dequant/attention shapes are dynamic and CANNOT be CUDA-graph-captured. To make the path graph-safe do NOT compact; keep a FIXED `[bs*width]` layout: every lane gets a compact row at ordinal `b*width + lane`, so the compact buffer is always `[bs*width, 1, 576]`. Masked / within-row-duplicate lanes write a SAFE in-bounds physical slot (e.g. `0`) into the dequant input (never `-1` — it is loaded) and `-1` into the compact index (the kernel masks it). A request then attends EXACTLY the same valid (post-dedup) slots as the eager builder — identical attention — in a capturable fixed shape. Pair it with an alloc-free `dequantize_k_cache_paged_out(quant, page_table, out)` writing into preallocated bf16 scratch (the allocating `dequantize_k_cache_paged` becomes a thin wrapper). The builder stays fully tensorized (no `.item()`, no dynamic boolean-mask shapes; reuse the stable-sort dedup); intermediates allocate from the graph pool during capture and replay alloc-free. PROVE it with a real `torch.cuda.CUDAGraph` capture of (fixed builder → dequant `out=` → `flash_mla_sparse_fwd`) + `assert_no_alloc_in_region(replay)` at 4096/8192, matching the eager reference — not just an allocation-free-eager pattern. (Fixed-shape is the load-bearing requirement; the `out=` variant is the polish — even an internal `torch.empty` is graph-pool-captured IF the shape is fixed, but eliminating it keeps the path cleanest.)
Production-wiring corollary (R17): allocate the fixed scratch once in the DS graph-state dataclass (`DSGraphState` + `allocate_graph_state`, sized `max_bs*max_top_k`, only when the opt-in flag is on) and route the decode method through it under capture — resolve the state from the BACKEND's own `self.forward_metadata` (a backend method, unlike a model hook, so no ForwardContext dance) with a `getattr` fallback to the eager builder so partial unit-test stubs and non-graph runs still work. q head-padding is also alloc-free: write real heads into a preallocated `[max_bs, required_pad_heads, d]` scratch; the pad-head TAIL stays `0` from the zero-allocation and is NEVER written (each head attends independently + the padded heads' output is trimmed), so no per-step zero is needed. The fixed `[bs*width]` compact_kv scratch is the footprint (`max_bs*lifted_width*576*2` B) — bound it with a low `--cuda-graph-max-bs` for this low-concurrency long-context lever. VALIDATE end-to-end with BOTH a wired-backend `_forward_lifted_budget` CUDAGraph zero-alloc replay AND a LIVE boot WITHOUT `--disable-cuda-graph`: decode batches must log `cuda graph: True` and serve correctly; note that the host-syncing per-request DS meta is `None` under graph (eager-only) — its absence CONFIRMS the decode ran captured, it is not a bug. The graph-mode served recall is the binding production number; here it matched eager (95% at 4K) because the budget is near-dense, and ran 3.4× faster.
Constraints: applies to the fp8 lifted-budget decode path; the bf16 `flashmla_sparse` decode path indexes the full cache by physical slot directly (no dequant/compact step), so this compact remap is specific to the fp8 op-point. The `%128` width and `<0/>=s_kv` masking are properties of THIS `flash_mla_sparse_fwd` build (sm90); re-verify if the kernel version changes. The fixed `[bs*width]` graph-safe layout dequantizes `bs*width` rows every step (wasteful when `valid_lengths << width`) — that is the cost of graph-capturability; keep the dynamic eager builder for non-graph runs.
Validation Evidence: loop7 R12 on 8xH200 (sm90). `test_lifted_budget_decode.py::TestCompactDecodeIndex` (8 CPU remap cases) + `TestLiftedBudgetKernelSmoke` (2 GPU smokes): the no-cap 3000@4096 match and the fp8 end-to-end + bit-identical gather. `width=8` reproduced the `topk % (2*B_TOPK)` assert; `width=256/4096` pass. 332 DS unit tests + 9 subtests pass. commit d187f59f4. R16: `dequantize_k_cache_paged_out` + `build_lifted_compact_index_fixed`/`build_lifted_compact_kv_fixed` + `TestLiftedBudgetGraphSafe` (CPU fixed-layout/dedup; dequant `out=` byte-identical; real-CUDAGraph zero-alloc replay at 4096/8192 matching the eager reference). 345 DS unit tests + 9 subtests pass. commit 714cf62b2. R17: wired into `DSGraphState`/`allocate_graph_state` + `_forward_lifted_budget` graph path + q-pad scratch + validator relax; `TestLiftedBudgetBackendGraphSafe` (wired-backend zero-alloc CUDAGraph replay 4096/8192); LIVE boot WITHOUT `--disable-cuda-graph` captured the full forward (`cuda graph: True`), graph-mode NIAH 4K N=20 = 95% (== eager), 3.4× faster, `m10_lifted_graph_finding.md`. 347 DS unit tests pass. commits 6453562e9 + 41e0af078.

## Lesson: nccl-collective-graph-capture-needs-runtime-not-unit-test
Lesson ID: BL-20260602-nccl-collective-graph-capture-needs-runtime-not-unit-test
Scope: any attempt to PROVE that a TP collective-using path (DS `retrieve_topk_graph_safe`'s SUM all-reduce, or any `dist.all_reduce`/NCCL collective inside a graph-captured region) is CUDA-graph-safe + cross-rank-deterministic via a standalone multiprocess unit test — `test_ds_scorer_tp_determinism.py`, and the graph-captured-TP-equality artifacts reviewers ask for.
Problem Description: A standalone N-rank unit test that spawns N processes, each binding a GPU + an NCCL process group, then captures a collective-using kernel in a raw `with torch.cuda.graph(g): _call_with_all_reduce()` and replays it — DEADLOCKS (hung past a 540 s timeout; had to SIGTERM + clean up orphan workers). Warming up the collective on a side stream before capture did NOT help. The naive expectation ("the production server captures the all-reduce under CUDA graph and works, so a unit test can too") is wrong about the HARNESS, not the path.
Root Cause: capturing an NCCL collective is not a per-rank-local operation — it needs cross-rank coordination that the CUDA-graph machinery only provides through the production capture path (the model runner's `cuda_graph_runner`: a shared graph memory pool, NCCL comm graph-registration, and all ranks entering capture in lockstep on the same pool). A raw per-rank `torch.cuda.graph(g)` in a spawned unit worker has none of that, so the captured collective hangs waiting for a coordination that never comes. The production path works precisely because `cuda_graph_runner` sets this up; the unit harness cannot replicate it cheaply.
Solution: do NOT try to capture the collective in a standalone unit test. Prove the same property by COMPOSED evidence: (a) a SINGLE-rank capture of the same selector/kernel with `process_group=None` (no collective) at the real widths — proves the per-rank compute + the top-k replay zero-alloc and is bit-identical to eager; (b) an EAGER N-rank test (gloo is fine) asserting cross-rank `selected_indices`/`valid_lengths` equality — proves the all-reduce is rank-symmetric + deterministic (SUM all-reduce gives identical all-reduced scores → identical selection); and (c) a LIVE boot of the real server WITH CUDA graph + TP=N that serves correct output (e.g. recall) — this is the actual collective-under-production-capture, and divergent ranks would corrupt the all-reduced result → degenerate output, so correct serving IS the cross-rank-under-capture proof. Document explicitly that the standalone NCCL-graph-capture artifact is infeasible (deadlocks) and that (c) is the real evidence; reviewers accept (a)+(b)+(c). If a stronger standalone artifact is ever needed, it must hook the production `cuda_graph_runner` (a runner integration probe that dumps/asserts equality under the real capture), not a raw `torch.cuda.graph` NCCL unit.
Constraints: applies to proving graph-safety/determinism of any TP collective path. The single-rank capture (a) still catches real per-rank graph-safety regressions (dynamic shapes, host syncs, alloc-on-replay); only the cross-rank-COLLECTIVE-under-capture coordination is what the unit harness cannot do. Set a hard timeout + clean up orphan spawned workers when experimenting (the deadlock leaves GPU-holding processes).
Validation Evidence: loop7 R18 on 8xH200. The 8-rank NCCL `retrieve_topk_graph_safe`-under-`torch.cuda.graph` test hung (540 s timeout, SIGTERM). Replaced with `TestLiftedWidthSelectionGraphCaptured` (single-rank lifted-width 4096/8192 capture, zero-alloc + bit-identical to eager) + the existing `TestTP8LiftedWidthDeterminism` (eager 8-rank equality) + the live R17 TP=8 graph server serving 95% recall (`m10_lifted_graph_finding.md`). ask-codex re-review: the (a)+(b)+(c) composition is an acceptable AC-4 production-readiness close; a raw per-rank NCCL `torch.cuda.graph` harness is NOT required. 350 DS unit tests pass. commit f9f6ec056.
Source Rounds: loop7 R18 (hit the NCCL-graph-capture deadlock proving the graph-captured TP=8 lifted-width selector equality; resolved with composed single-rank-capture + eager-cross-rank + live-runner evidence).
