## Lesson: ds-selector-width-graph-ladder-is-decode-critical
Lesson ID: BL-20260619-ds-selector-width-ladder
Scope: python/sglang/srt/model_executor/runner/decode_cuda_graph_runner.py; python/sglang/srt/layers/attention/dsa_backend.py (_ds_graph_variant_key / _ds_decode_metadata_key / _ds_shared_graph_state); Double Sparsity decode under CUDA graph
Problem Description: A clean DS port booted, was genuinely active (meta_info["double_sparsity"] selected=2048<total, dense_fallback=0), passed all functional gates, but conc-64 p50 decode TPS was 18.8 (vs ~26.9 ref) and P99 TTFT 39s (vs 25s). Native DSA on the SAME base was 26.06/46.5s, so decode (18.8<<26.06) was a PORT regression, while TTFT was base drift.
Root Cause: The DS selector-width graph ladder lived in the OLD monolithic cuda_graph_runner.py, which upstream refactored away into model_executor/runner/. The port carried the dsa_backend half (the _ds_graph_variant_key consumer) but NOT the runner half that STAMPS it, so _ds_graph_variant_key stayed None -> the captured decode graph scored the FULL req_to_token width (~202756 here, 40x the 5120 bucket) every step. Deferring the runner ladder as a "no-op for the default config" was wrong: selector_width_buckets defaults to (5120,), and full-width selection collapses decode throughput.
Solution: Retarget the ladder onto DecodeCudaGraphRunner: compute_ds_selector_widths(buckets, full_width, policy) + ds_covering_width; in __init__ build self.ds_selector_widths when DS-on decode; in the capture loop capture one graph per width, stamping attn_backend._ds_graph_variant_key=(bs,width) around capture_one_shape (it flows into init_forward_metadata_out_graph -> _apply_cuda_graph_metadata); in replay_prepare pick the smallest width covering the live seq_lens and stamp it. Key each width's graph by a width-encoded variant_label (f"dsw{width}") so no ShapeKey dataclass change is needed. Result: 29.34 TPS / 23.29s -- within the loop-11b band and ahead of DSA. A high full-width is the tell (log "DS selector-width graph variants").
Constraints: Decode-only (capture_forward_mode==DECODE, not pdmux/encoder-decoder/spec). full_fallback keeps the full-width graph for seq>bucket; with padding enabled can_run gates on bs<=max_bs (not the width key), so every captured width must exist for the padded bs (it does). The width must be measured against real seq_lens_cpu[:raw_bs], never padded buffer rows.
Validation Evidence: development/loop12/perf_evidence/verdict.json (29.34/23.29 parity:true) vs dsa_evidence (26.06/46.50) and the no-ladder run (18.81/39.15); v2 commit e6fda2fe9.
Source Rounds: loop12 R0.

## Lesson: branch-off-latest-main-drags-kernel-and-triton-floors
Lesson ID: BL-20260619-latest-main-base-drift
Scope: serving any feature branch cut off LATEST origin/main vs the older main a feature was validated on (sgl-kernel version, triton MoE configs)
Problem Description: A DS branch cut off latest main (per a "branch off latest main" decision) crashed at boot with `flash_attn_varlen_func() got an unexpected keyword argument 'only_qv'`, then once booting showed a per-MoE-layer "triton_3_6_0 config not found -> fallback to 3_5_1, Performance might be sub-optimal" warning, and conc-64 TTFT was ~46s for BOTH DS and native DSA (vs 25s on the validated dev base).
Root Cause: Latest main genuinely USES newer deps the validated base did not: its jit_kernel flash-attention path calls the sgl-kernel 0.4.4 only_qv kernel (env had 0.4.3; dev base required only 0.4.2.post2), and it expects triton 3.6.0-tuned MoE configs that aren't bundled (env has triton 3.6.0 -> falls back to 3.5.1-tuned configs). Neither is the feature's fault; the absolute perf reference (measured on the older base) is not apples-to-apples on latest main.
Solution: For boot, install the real floor (`pip install sglang-kernel==0.4.4`, prebuilt abi3 wheel) rather than SGLANG_SKIP_SGL_KERNEL_VERSION_CHECK (the skip is insufficient when the code truly calls only_qv). For the parity verdict, isolate port-vs-base by measuring native DSA on the SAME latest-main base: if DSA also regressed (TTFT 46s here) the base is the cause; reframe the gate as "feature within band of native-on-same-base" rather than vs the old absolute. Surface the base-drift to the human before re-architecting; it can justify re-basing to the validated main.
Constraints: Branching off latest main is a clean PR base but NOT a faithful perf-reproduction base. Always capture a same-base native baseline before declaring a perf regression a port bug.
Validation Evidence: development/loop12/serve_ds_boot.log (only_qv crash + MoE fallback); dsa_baseline.out (DSA 26.06/46.50 on latest main); loop12 goal-tracker Plan Evolution Log.

## Lesson: perf-parity-must-pin-exact-request-shape
Lesson ID: BL-20260619-perf-parity-pin-request-shape
Scope: benchmarks/bench_double_sparsity.py and any perf-parity gate over sglang.bench_serving generated-shared-prefix (gsp)
Problem Description: A conc-64 perf-parity wrapper claimed to "mirror the loop-11b workload exactly" but only passed the per-request lengths (--gsp-system-prompt-len/--gsp-question-len/--gsp-output-len), range-ratio, max-concurrency, --num-prompts, and seed. The saved verdict recorded num_prompts=256 yet the run completed 1024 requests, so the 29.34-TPS datapoint was on the wrong request distribution and was rejected as AC-8 proof.
Root Cause: The stock generated-shared-prefix dataset is generated from --gsp-num-groups (default 64) x --gsp-prompts-per-group (default 16) and effectively IGNORES --num-prompts. The loop-11b recipe pinned NUM_GROUPS=1 and --gsp-prompts-per-group ${NUM_PROMPTS} (one shared system prompt across all requests). Omitting those two flags silently benchmarks 64 prefix groups x 16 prompts = 1024 reqs — a different prefix-reuse shape than the validated single-group workload.
Solution: Pin --gsp-num-groups 1 and --gsp-prompts-per-group <num_prompts> in the wrapper. Record gsp_num_groups, gsp_prompts_per_group, expected_prompts, and actual_completed (from result["completed"], falling back to len(output_lens)) in the verdict, and FAIL CLOSED if actual_completed != num_prompts so any future dataset-shape drift cannot pass silently. After fixing, the corrected single-group conc-64 run gave 256/256 completed, p50 decode TPS 35.05 / P99 TTFT 22.90s.
Constraints: A parity gate must validate the request SHAPE, not just per-request lengths; a green TPS/TTFT band on the wrong shape is not parity. Keep the benchmark itself stock bench_serving — only the wrapper pins args.
Validation Evidence: development/loop12/perf_evidence/verdict.json (actual_completed=256, gsp_num_groups=1, request_shape_ok=true, parity=true) vs the pre-fix m6m8_eval_ladder.out (gsp_num_groups=64, 1024 completed); v2 commits 5dcd73ca6 + f05326636.
Source Rounds: loop12 R1.

## Lesson: ds-meta-under-cuda-graph
Lesson ID: BL-20260617-ds-meta-under-cuda-graph
Scope: python/sglang/srt/layers/attention/dsa_backend.py; python/sglang/srt/model_executor/model_runner.py; any per-request side-channel/metric for a graphed decode backend
Problem Description: The per-request Double Sparsity summary (meta_info["double_sparsity"].{sparsity_rate,selected_tokens,dense_fallback}) was null for GLM-5.1, so the fail-closed trial_evidence.py REFUSED every published SLO trial. The model-side publisher (_publish_ds_request_summary) only fires on DeepseekV2's attention; GLM uses Glm4MoeAttention + the dsa backend. A naive fix that publishes from the backend's forward_decode (reading the selected page table) populated 0/64 in a smoke test.
Root Cause: Decode runs under CUDA-graph REPLAY, where the Python in forward_decode never executes (the captured CUDA ops replay, the host code does not). So a publish placed in the graphed forward never runs for the measured steps. And a per-step device->host read of the selected page table (page_table_1 >= 0).sum() would force a sync that serializes graph replay and perturbs the very decode-throughput numbers the verdict depends on.
Solution: Publish host-side, with NO GPU sync, from a per-step hook that runs for BOTH eager and graph decode: the model_runner post-forward transport. Derive the count deterministically from host tensors + the selector's contract: the table-free DS selector keeps min(top_k, valid_tokens) positions, and for decode valid_tokens == seq_len, so selected = min(ds_max_top_k, forward_batch.seq_lens_cpu[i]); total = seq_len; dense_fallback = 0. Gate on enable_double_sparsity + decode mode; do not overwrite an existing model-side summary. Verified zero decode-timing impact (dedicated tax-probe ITLs unchanged to 0.1ms).
Constraints: The replay hook init_forward_metadata_replay_cuda_graph has no forward_batch arg, so it cannot attach the summary; the transport (model_runner) is the single host-side per-step point that has forward_batch. is_current_stream_capturing()-gating alone is insufficient (it covers capture, not replay). Keep plan-workflow terminology (AC-/DEC-) OUT of the implementation comments.
Validation Evidence: development/loop11b/runs/20260616_mb/results_r2/ (all 6 DS trials trial_evidence.py PASS: dense_fallback_total=0, selected_tokens_mean 2048 < total ~3590); smoke_ds_meta.sh PASS; commit b0e448b1.

## Lesson: ds-dense-degradation-is-current-decode-slot-exclusion
Lesson ID: BL-20260620-ds-current-slot-exclusion
Scope: python/sglang/srt/models/deepseek_v2.py _select_topk_indices (the _slot_written current-slot invalidation); Double Sparsity MLA decode selection on GLM-5.1-FP8; any DS-vs-DSA accuracy diagnosis
Problem Description: Table-free DS scored GSM8K 0.620 dense / 0.000 sparse vs native DSA 0.975/0.953 on GLM-5.1-FP8 (8xH200 TP=8, temp 0, completion API). The dense degradation was the puzzle: at seq~716 < top_k 2048 selection is a no-op (DS keeps 715/716 tokens), yet DS scored 0.620 on the SAME tokens through the SAME flash_mla_with_kvcache kernel DSA uses.
Root Cause: The DS selection path drops exactly the CURRENT decode slot. _select_topk_indices invalidates it in the _slot_written bitmap (`_slot_written[layer_id, out_cache_loc] = False`) BEFORE scoring so a reused physical KV slot's stale latent can't be selected; the companion restore only lands after the KV write. So within the same decode step the current token's own slot scores -inf and is excluded from its selected attention set -> every decode token fails to attend to itself -> dense 0.62, and at long context (compounded with real pruning) sparse collapses to 0.000. This is downstream-of-selection / slot-validity (H3), NOT the scorer/perf-opts and NOT an algorithm-transfer failure.
Solution: (DIAGNOSIS ONLY — no fix landed this loop.) The recommended fix for a follow-up loop: force-include the current decode slot in its own selection/attention set, or restore _slot_written for the current slot before the selected set is consumed. The DIAGNOSTIC METHOD that nailed it (reusable): (1) build a perf-NAIVE fp32-EXACT reference selector (dequant latent to fp32, exact absorbed channel-dot, exact full-width torch.topk) — if it scores identically to production, the ENTIRE scorer + every perf-opt is exonerated in one shot (stronger than retiring suspects one at a time); (2) a forced-all / anchor-recency control that force-includes tokens isolates downstream-of-selection from scorer; (3) sweep the anchor budget (b=1 vs b=64) to isolate a SINGLE token (current slot, b=1 -> 0.970) and to separate a clean dense bug from a confounded sparse one.
Constraints: The reference selector must run EAGER (--disable-cuda-graph; host-side dequant/sync is illegal under graph capture) and gate on decode-with-state (3-D [bs,H,head_dim] cuda queries) so prefill/extend forwards fall through to production handling. channel_selection/channel_weights are global [num_ds_layers,H,label_dim] — index by layer_id; absorbed_w_sel is already the layer's [H,label_dim,lora]. Dequant only the gathered live slots, never the full KV pool (full-pool dequant per layer per step is intractable; gather-then-dequant is identical fp32 and orders cheaper). The sparse 0.000 stays CONFOUNDED by this bug until it is fixed — do not attribute sparse to H0/H2 before re-measuring post-fix.
Validation Evidence: development/loop13/ROOT_CAUSE.md + evidence/evidence_table.md + evidence/findings.md + evidence/codex_review_h3.md. Key arms: production DS 0.620/0.000; fp32-exact reference 0.620/0.000 (scorer exonerated); forced-all dense 0.950; anchor-recency b=1 (current-slot only) dense 0.970 / sparse 0.000; b=64 dense 0.960 / sparse 0.007. Codex (gpt-5.5 xhigh) reviewed and the current-only + sparse-sweep refinements were run.
Source Rounds: loop13 R0.

## Lesson: ds-sparse-collapse-is-the-rawdot-scorer-norm-off-lock
Lesson ID: BL-20260620-ds-rawdot-scorer-lock
Scope: python/sglang/srt/layers/attention/double_sparsity/config.py (scorer_norm hard-lock "off"); absorbed_latent.py (reference_cosine); Double Sparsity long-context (sparse) selection on GLM-5.1-FP8
Problem Description: Production table-free DS scored GSM8K sparse (24-shot, ~5.6k tok > top_k 2048) at 0.000 vs DSA 0.953. A perf-naive fp32-EXACT raw-dot reference (H3-clean: current decode slot included, TF32 off) STILL scored only 0.013 — so the sparse collapse is not the H3 current-slot bug and not fp8/bf16/radix/width perf-opts. Yet a perf-naive fp32 COSINE reference (same setup) scored 0.940 ~= DSA. The whole DS path looked like the algorithm/mask just doesn't transfer (a false "H0/H2" read), when really the sparse failure is the SCORER.
Root Cause: config.py hard-locks scorer_norm="off" (raw channel-dot) because the table-free absorbed-latent identity score=max_h v_h·c_kv only holds for the raw dot; the Loop-11 table-free rewrite (01e3ff238, deletes TokenLabelTable) thereby DROPPED the Loop-7 cosine scorer (Loop 7 had measured cosine lifting 16K NIAH recall 5%->40%). The raw channel-dot is dominated by per-token latent magnitude at long context, so its top-2048 misses the tokens the model needs; cosine (direction-only) selects the right tokens. So "going table-free" silently reverted to the known-bad raw-dot scorer for the sparse regime.
Solution: (DIAGNOSIS ONLY — no fix landed.) Recommended FIX (follow-up loop): restore a cosine scorer for the table-free path — you do NOT need to rebuild TokenLabelTable; the cosine norms are computable from the bind-time absorbed projection: |K_label_h[t]| = ||absorbed_w_sel[h] @ c_kv[t]|| (absorbed_w_sel[h] ARE the mask-channel rows of the per-head K-noPE up-projection) and |Q_label_h| = ||w_c ⊙ q_{S_h}||, normalizing AFTER the mask-channel gather. DIAGNOSTIC METHOD (reusable): a perf-naive fp32 reference selector that can toggle raw-dot vs cosine and force-include the current slot turns "does the algorithm transfer?" into a one-variable GSM8K experiment; prove the materialized-signature path is selection-equal to the absorbed raw-dot (cosine numerator with normalize=False) so cosine-vs-rawdot isolates ONLY the normalization. With a GOOD best-of(raw,cosine) ceiling, the BAD-branch no-mask ablation becomes moot (the same mask reaches ~DSA under cosine, so the mask is adequate).
Constraints: cosine reference is eager (--disable-cuda-graph) and memory-heavy at long context (materialized K_label [bs,S,H,label_dim]); drop concurrency for sparse batched to avoid OOM. The sparse cosine win classifies as a design-constraint/perf regression of the table-free rewrite (H1-family), NOT H0/H2. Dense is a SEPARATE bug (current-slot exclusion, see BL-20260620-ds-current-slot-exclusion).
Validation Evidence: development/loop13/ROOT_CAUSE.md + evidence/gate_ac5.md + evidence/evidence_table.md + evidence/codex_review_gate.md + development/loop13/test_reference_selectors.py. Faithful raw-dot 0.950/0.013; faithful cosine 0.940/0.940; DSA 0.975/0.953; gate=GOOD. Codex (gpt-5.5 xhigh) verified the gate + the cosine-vs-rawdot single-variable attribution (materialized-raw == absorbed-raw selection proven on CPU).
Source Rounds: loop13 R1.

## Lesson: ds-capture-run-both-topk-on-one-row-not-cross-instrument-join
Lesson ID: BL-20260621-ds-capture-step-alignment
Scope: python/sglang/srt/layers/attention/double_sparsity/{score_capture.py,selection_capture.py}; offline analysis of DS capture .pt dumps (analyze_captures.py)
Problem Description: Joining score_capture rows to selection_capture rows to check radix-top-k == torch.topk looked done but gave nonsense (jaccard ~0.6 with prod_k==ref_k, which is impossible if the score row is the radix's input). Two latent bugs: (1) the analyzer did a cross-record CARTESIAN comparison (every score row vs every selection row) because selection_capture had no req_pool_index; (2) even after adding req_pool_indices and joining exactly (unmatched=0), the numbers stayed wrong.
Root Cause: score_capture's filename is rank{tp}_req{req}_layer{layer}.pt with NO decode-step id, so it is OVERWRITTEN across the extend+decode forwards of a request — the persisted score row is not reliably the SAME decode step the radix selected from. selection_capture and score_capture also use INDEPENDENT step counters, so even adding a step to score_capture would not align them. So the captured score row and the captured selection are from different steps.
Solution (R4, the clean one): DO NOT join captured selection rows to captured score rows at all. The captured post-reduce score row IS the authoritative top-k input the production radix consumed, so run BOTH top-k methods on the SAME captured score row and compare selected sets: select_topk_sequence_order (exact == torch.topk) vs blocked_topk_sequence_order (the production blocked/radix ALGORITHM). Identical ⇒ radix == torch.topk on real score distributions, with zero alignment needed. Result on real GLM-5.1 rows: 624/624 identical, plus selector-width [5120]==full 624/624 (verify_ac2_3.py → evidence/ac2_3_radix_width_equivalence.json). The earlier cross-instrument join path (shared decode-step id stamped into both captures) is a valid but heavier alternative; prefer re-running both algorithms on one captured input when that input is the algorithm's direct argument. (Earlier R2-R3 attempt: added req_pool_indices for an exact (req_pool_index,layer) join, but score_capture has no decode-step id and uses an independent step counter, so the join was valid yet the score-vs-selection pairing was misaligned → 81/546 artifact; superseded by the direct method.)
Constraints: score_capture/selection_capture only fire under their config flags + --disable-cuda-graph (host copies). Analyzers over captures must fail-CLOSED: assert nonzero rows and (for joins) unmatched_rows==0, exit nonzero otherwise — a clean-looking artifact must never be produced from an empty/stale/incomplete capture set. CRITICAL (R5): the captured rows must EXERCISE the branch being tested — see [[ds-topk-control-must-exercise-pruning]]; the R4 624/624 ran on seq_len=13 smoke rows where top_k(2048) > seq_len, so both methods trivially selected all positions (a select-all sanity check, not a pruning proof).
Validation Evidence: development/loop13/verify_ac2_3.py + evidence/ac2_3_radix_width_equivalence.json. R5 pruning-valid: 4992/4992 radix==torch.topk and 4992/4992 width==full on real SPARSE captures (median seq_len 4280, 2048 of ~4280 pruned). The R4 624/624 was on seq_len=13 smoke captures and is INVALID for the sparse regime. analyze_captures.py + verify_ac2_3.py fail-closed (exit 2 on zero/unmatched/zero-pruning rows).
Source Rounds: loop13 R2-R5.

## Lesson: ds-topk-control-must-exercise-pruning
Lesson ID: BL-20260621-ds-control-must-exercise-pruning
Scope: any selection/top-k equivalence control over captured score rows (development/loop13/verify_ac2_3.py); more generally any control meant to retire a suspect on the "risky branch"
Problem Description: An AC-2.3 control "proved" the production radix top-k == torch.topk and selector-width [5120] == full at 624/624 identical, and it was marked RESOLVED — but every captured score row had seq_len=13 while top_k=2048. With seq_len < top_k BOTH algorithms select every finite position, so the comparison is a select-all tautology that exercises ZERO pruning and ZERO width bucketing. It cannot retire a radix/width suspect for the sparse regime where the production path selects ~2048 of ~5.6k. ## Lesson: niah-recall-oracle-fail-closed-span-self-verify
Lesson ID: BL-20260621-niah-recall-oracle-fail-closed-span-self-verify
Scope: reusing a model-specific NIAH selection-recall oracle on a NEW model (development/loop13 AC-2.4: a DeepSeek-V3.2-era recall-oracle driver re-pointed at GLM-5.1-FP8); any harness that registers token-position spans cross-process to a server worker
Problem Description: The recall-oracle (oracle_artifact_sink.py + selection_recall_oracle.py + the selector hook at selection_kernel.py:1210) was wired and proven on DeepSeek-V3.2, but the loop7 driver (niah_oracle_sweep.py) was unusable here: its test/manual helper was deleted AND it hard-codes the V3.2 tokenizer / prompt construction. AC-2.4 needs recall@2048 on GLM for dense + sparse. Two silent-correctness hazards: (1) the needle's LOGICAL token span MUST match the server's KV positions — a constant BOS-prefix shift (or any add_special_tokens difference) misaligns every span by a constant, and the oracle would then measure the WRONG tokens' rank without obviously failing (a +1 shift is not span_out_of_range). (2) cross-process path agreement: env vars set at server launch do NOT reach SGLang TP worker subprocesses, so the worker resolves the sink/trial dir from ITS cwd default — a driver that sets the dir only via its own env silently writes/reads a DIFFERENT dir than the worker (the "silently-absent records" failure).
Root Cause: the server-side oracle (rank/recall math) is model-agnostic and reusable AS-IS; only the DRIVER (tokenizer + NIAH prompt + needle-span + cross-process paths) is model/deployment-specific, and the span/path details are exactly where a subtle mismatch produces a plausible-but-wrong artifact.
Solution: write a SELF-CONTAINED driver that reuses only the model-agnostic sink API (set_active_trial/clear_active_trial/default paths) + the server oracle. (a) ALIGNMENT PROBE: before the measured trials, send one /generate per regime, compute delta = server_prompt_tokens - offline_tokens(add_special_tokens=False), assert it is a SINGLE consistent small offset (0 or 1) across regimes, and shift every registered span by delta (GLM measured delta=0 — no BOS; a BOS model would be 1). (b) FAIL-CLOSED backstop: rely on the oracle emitting a span_out_of_range hard-failure marker when a registered span is out of range, and make the driver exit non-zero on ANY hard-failure marker OR any issued trial that produced no record — so a misaligned span fails LOUD, never silent. (c) CROSS-PROCESS PATHS: launch the server with a known cwd (here evidence/) so the worker's default sink/trial dir (cwd/.sglang_ds_oracle) is deterministic, and point the driver at that same ABSOLUTE dir; don't depend on launch-time env reaching the worker. (d) regime semantics: dense (prompt<top_k) selects all tokens so recall@2048 is trivially 1.0 (a sanity floor, corroborating the dense regime is selection-complete, NOT a scorer result); sparse (prompt>top_k) is the informative measurement. (e) ledger fail-closes on a missing/empty artifact before rendering AC-2.4 present.
Constraints: recall@K is a SCORE-RANKING property on a NIAH task, NOT a generic selected-index equivalence proof and NOT scorer exoneration (plan AC-2.4/DEC) — label the artifact corroboration_only and keep claims to "the scorer ranks the needle in the budget X% of the time". Cross-check the AC-1 oracle invariant recall@index_topk == selected_contains_needle (both 1.0 dense, both 0.4103 sparse here) as an internal-consistency guard. The needle must be a contiguous, findable string (prompt.find) and the recall is decode-time (DS selection runs only in decode → ignore_eos + a few decode steps).
R19 HARDENING (Codex caught a fail-OPEN wrapper around correct numbers — same evidence-integrity class as the R15 forced-all-vs-scored regression): a "fail-closed" producer that WRITES THEN CHECKS still leaves a canonical artifact on failure. Three fixes, each its own footgun: (1) write the canonical artifact LAST, via atomic `.tmp`→`os.replace`, ONLY after every check passes — never `json.dump(canonical)` before the `problems` gate; a partial/failed run must leave the canonical artifact UNTOUCHED. (2) treat EVERY failure marker as fatal, not a hand-picked whitelist — the server records `no_active_trial` as a fail-closed marker too, so the gate is `sum(failure_markers.values()) == 0`, NOT `span_out_of_range/exception` only. Beware the defaultdict footgun that hid this: `sum(d[k] for k in WHITELIST)` INSERTS those keys (so the artifact showed `{span_out_of_range:0, exception:0}` and silently ignored others) — sum over `d.values()`. (3) assert COUNT invariants so a partial run can't pass: per regime trials_issued==num, trials_with_records==issued, oracle_records==recall_records==selected_records, recall==selected_rate (the AC-1 per-row invariant), non-null server prompt_tokens for every issued trial. The CONSUMER (build_ledger.validate_recall_oracle_artifact) must be an INDEPENDENT gate asserting the SAME invariants + zero markers + source basename — never render an AC present from a nearby JSON by presence alone. And the cross-process CWD agreement must be BAKED INTO the serve harness, not merely documented: `serve.sh` got a `LAUNCH_CWD` var (default caller PWD; `ds_recall_oracle` sets `$EVID`) and launches via `( cd "$LAUNCH_CWD" && exec python3 -m sglang.launch_server … )` with LOG/PIDFILE absolute (`exec` keeps `$!`==server PID for teardown) — proven by re-running the sweep with serve.sh invoked from the REPO ROOT (no manual cd/env), records landing in the driver's default dir. Verified with explicit NEGATIVE tests: producer offline (no_active_trial / missing-trial / null-tokens → exit 2, no canonical write) + ledger (partial / failure-marker / missing-regime / wrong-source / recall-mismatch / null-sample → abort).
